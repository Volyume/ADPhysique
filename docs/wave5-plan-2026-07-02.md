## PART A — C5 TRAINING PARTNER v2

### What exists today (the base v2 extends)

- Partner data is registry-synced, PAIR-scoped, LWW (`src/lib/sync/registry.js:187-200`,
  handler `src/lib/sync/tables/partners.js`). The only shared payload is the
  derived week signal `{ planned_count, done_count, week_met, state }`
  (`src/lib/partners/service.js:137-146`), produced by the single seam
  `computeWeekState` (`src/lib/streak.js:80-92`).
- The §5 privacy rule ("derived only — NEVER weights, sets, reps, body weight,
  food, calories …", `docs/bp-partner-system-rebuild.md:38-41`) is enforced
  structurally: the cloud tables have no columns for raw data (`migrate_081`),
  the ED flag freezes the outbound signal to `resting`
  (`src/lib/partners/weekSignalWriter.js:56-57`, pinned
  `weekSignalWriter.test.js:38-44`), unpair purges through the server RPC
  (`service.js:117-127` → `migrate_092`, pinned `service.test.js:89-99`).
- Pro-gated (`RootNavigator.js:184-187`); one screen (`PartnerScreen.js`),
  plus post-workout beat (`WorkoutSummaryScreen.js:806-833`) and Progress tile
  (`AnalyticsScreen.js:598`).

### The two infrastructure gaps the sweep found (why C5 needs a decision)

1. **No stable cross-user programme identity.** Library plan IDs are random per
   install (`seedRoutines.js`, "plan IDs are random UUIDs"); the only lineage
   that survives copying is `routines.source_routine_id` and the plan *name*
   (`copyPlanFromLibrary` `database.js:2911-2933` does NOT set
   `programmes.source_programme_id`). So "train the same block" has nothing to
   join on today without new infra.
2. **No per-session schedule.** Scheduling granularity is weekday + fixed clock
   time (`@volyume_schedule_v1`, `trainingReminders.js:12`), and there is **no
   production writer** of that schedule key anywhere in `src/`. So a "cheer
   window around scheduled sessions" cannot anchor to a real session datetime;
   the nearest real anchor is the weekday training reminder.

→ **Founder decision C5 (Q3 below): which halves of v2 to build**, given
neither half's infra exists yet.

### Constraints any C5 build must honour (non-negotiable, from source)

- No weight/food/calorie sharing, ever — the shared payload stays the derived
  `computeWeekState` object (`streak.js:69`); any new shared field passes the
  same "derived only" test and gets a schema with no raw columns.
- ED freeze carries to every new surface (`weekSignalWriter.js:57`).
- Unpair/delete purge extends to any new shared table (`migrate_092` pattern;
  the delete-account + `delete_user_data` fallbacks `migrate_096:158-188`).
- A "cheer window" push is an **event-class** notification into a LOCKED doc:
  it needs a `categories.js` entry, a `notificationRoute.js` route, a
  `budget.js` priority slot (partner_cheer is currently lowest, 8th), quiet-
  hours shifting, schedule-time ED gating, a server-side recipient ED check,
  and a disable path — and the budget addendum is founder-reviewed
  (`NOTIFICATIONS_LOCKED.md:194`). New category = a founder-recorded deviation.

### Proposed increments (pending Q3)

- **A0** (decision-independent groundwork): a source-level privacy regression
  guard for `src/lib/partners/` — the sweep found there is NO source-text guard
  today, only behavioural tests. Pin: no partner write path serialises any
  weight/food/measurement field; the shared payload shape stays the 5 derived
  fields. This hardens the §5 contract before v2 widens the surface. Safe,
  additive, no product decision.
- **A1–A3**: shaped by Q3 (shared-programme compare / timed cheer / both).

## PART B — C2 MICRONUTRIENTS / UK NRV (MN-1)

### Blueprint & resolved blockers

Source: `docs/ultimate-audit-2026-06-13/pass4-blueprints-micronutrients.md`
(read in full). Its one BLOCKING open question NA-mn-1 (schema authority) is
**resolved**: CLAUDE.md makes `supabase/migrate_NNN_*.sql` canonical
(`schema.sql`/`setup_complete.sql` are stale snapshots), so a migration can be
written. Next free numbers: local `SCHEMA_MIGRATIONS` append
(`database.js:341`); cloud `migrate_099_*` (last is 098). NA-mn-4 (Pro gate)
resolved: the food/diary domain is already Pro (`RootNavigator.js:179,463`).

### What exists (the precedent to scale)

- Foods carry macros + `fibre_100g, sodium_100g, sugar_100g` per 100g and
  nothing else (`database.js:834-878`, cloud `migrate_015:19-39`). No
  vitamins/minerals anywhere in `src/` or `supabase/` — MN-1 is unstarted.
- **The seed sources already fetch micronutrient data and discard it**:
  OpenFoodFacts barcode returns the whole `nutriments` blob but the mapper
  `_toRow` keeps only kcal/P/C/F/fibre (`sources/liveOff.js:34-56,73`); USDA
  discards its full panel (`normalisers/usdaToFood.js:15-34`); the CoFID CSV
  carries the complete panel but `buildCofidSnapshot.js:56-57,162-164` extracts
  only fibre+sugar. So the ingestion pipes exist; MN-1 widens the field maps.
- **A pre-existing sync-seam gap** (decision-independent, fixable now):
  `_customFoodToCloud` OMITS `sodium_100g/sugar_100g` (`foodDomain.js:139-157`)
  even though the cloud RPC accepts them (`migrate_090:249-273`) and the pull
  applier reads them (`db.js:1430-1437`). MN-1's new columns must pass this
  seam, so it gets fixed as part of B0.
- U6 (`femaleNutritionAwareness.js`) is **awareness copy only**, keyed on sex,
  reading no data (header lines 6-10). "Full U6" = real iron-vs-NRV tracking,
  which is exactly what MN-1 unlocks (05-enhancements:344-347).

### The genuine forks (why C2 needs decisions)

- **Nutrient SET** — each nutrient is a column across local + cloud + seed +
  UI. The blueprint says "key vitamins and minerals," newbie-safe behind a tap,
  not Cronometer's 84 (`blueprint:31,62`). Which set? → **Q1**.
- **ED-safety posture of the panel** — a per-nutrient "% of NRV complete"
  score is a completeness pressure the ED-safety system exists to avoid;
  intake-with-plain-context is safer. The blueprint says "per-nutrient total vs
  UK NRV" but does not rule on scoring or flag-suppression. → **Q2**.

### Constraints any C2 build must honour (from source + rules)

- Every migration ADDITIVE + idempotent + headered (purpose / applied status /
  safe-to-re-run / rollback); cloud migration is FOUNDER-RUN, never app-run
  (`docs/rules/supabase.md`, CLAUDE.md §2). New tables (an NRV reference table)
  get full RLS or are static constants (no user data → constants preferred).
- Missing micros render "unknown", never 0 (`blueprint:48,58`).
- NRV maths UK-compliant (UK NRV reference values, not US RDA; blueprint:59-60).
- Sentry scrub already covers `^fibre/^sodium/^sugar` + `_100g`
  (`sentryScrub.js:47-60`); extend the scrub to the new columns so no
  micronutrient intake ever reaches Sentry (data-minimisation).
- Micronutrient totals stay OUT of any coaching-engine input — display-only,
  exactly as sodium/sugar are today (`macros.js:49-50`,
  `nutrientSummary.js:5-8`). The deterministic engine never sees them.

### Proposed increments (pending Q1/Q2)

- **B0** (decision-independent): fix the `_customFoodToCloud` sodium/sugar sync
  gap + extend the Sentry scrub patterns; pure correctness + minimisation, no
  schema, testable now.
- **B1**: UK NRV reference constants module (pure data, chosen set per Q1) +
  its unit tests. No I/O, no schema, reversible.
- **B2**: local SQLite migration — nullable micronutrient columns on `foods` +
  `custom_foods` (per Q1); idempotent, additive.
- **B3**: cloud migration `migrate_099_*` (founder-run) mirroring B2 + the
  food_sync RPC field maps; the sync mappers (`foodDomain.js`) carry the new
  columns both ways.
- **B4**: seed importers — widen `liveOff._toRow`, USDA normaliser, and the
  CoFID snapshot builder to keep the chosen nutrients; rebuild the bundled
  snapshots.
- **B5**: the opt-in `MicronutrientPanel` under the diary day (per Q2 posture),
  Pro-gated, "unknown not 0", suppressed-or-not per the ED decision.
- **B6**: turn the U6 awareness card into a live "your iron this week vs NRV"
  read where data exists (the "full U6" unlock), keeping the awareness copy as
  the empty/low-data state.

## FOUNDER DECISIONS — ANSWERED 2026-07-02

- **Q1 (nutrient set) = U6-completing core (5):** iron, calcium, vitamin D,
  B12, vitamin C. B1's NRV reference table and every C2 column/seed/UI is scoped
  to exactly these five. This directly turns the shipped U6 awareness card into
  live iron-vs-NRV tracking (B6).
- **Q2 (panel posture) = plain bands + flag-suppress:** the MicronutrientPanel
  shows intake with plain context ("enough" / "below typical"), NO per-nutrient
  percent-complete score, and the whole panel is suppressed under an open ED
  flag / calm mode like other food-adjacent surfaces. No completeness pressure.
- **Q3 (C5 scope) = full shared block:** add a stable shared-programme id both
  partners adopt, as a NEW registry-synced table with full RLS, so "train the
  same block" is explicit rather than name-matched. The unpair + delete-account
  + `delete_user_data` purge paths all extend to it. This is the larger C5;
  the completion compare rides the existing derived week signal (no raw data).

### Build order given the decisions

C5 (now a proper multi-increment build with a new shared surface) ships first;
C2 alone after. Increment map:

- **A0** — partner-privacy source guard (decision-independent). START NOW.

  extension (decision-independent correctness/minimisation).
- **B1** — UK NRV reference constants for the five nutrients (pure data).
- **B2/B3** — local + founder-run cloud migration (nullable columns for the
  five) + sync field maps.
- **B4** — seed importers widened to keep the five (OFF, USDA, CoFID builders).
- **B5** — opt-in `MicronutrientPanel` (plain bands, unknown-not-0,
  flag-suppressed, Pro).
- **B6** — U6 card becomes live iron-vs-NRV where data exists; awareness copy
  stays as the empty/low-data state.

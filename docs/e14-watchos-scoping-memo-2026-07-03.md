# E14 — watchOS scoping memo

Date: 2026-07-03. Memo only — no code, no project changes. Decision context:
the founder has decided Volyume WILL add watchOS support; this memo makes the
build plannable. Every factual claim is grounded in
`docs/watchos-scoping-evidence-2026-07-02.md` (section references below);
claims that pack marked UNVERIFIED are carried as such, never firmed up.

Ground truths, stated for the record (evidence §4.3, §6.2):
- React Native does not run on watchOS. The watch app is a NATIVE SwiftUI
  target in the iOS project, talking to the phone over WatchConnectivity.
  This is new-platform work, not a port.
- Sustained background runtime on the wrist (a rest timer that survives
  wrist-down, sensor access) effectively requires running an
  HKWorkoutSession — HealthKit territory.

---

## 1. THE HEALTHKIT GATE — decide this first, in isolation

### Path 1 — WITHOUT HealthKit
What it actually delivers (evidence §1): the app lives ~2 minutes frontmost,
then suspends; wrist-down suspends timers; there is NO fitness-eligible
extended-runtime session type (self care 10 min / mindfulness / physical
therapy / smart alarm are the whole list, none honestly ours). The one
reliable wrist beat is the same trick the phone already uses: a wall-clock
local notification whose haptic fires even while the watch app is suspended
— though the phone-to-watch notification ROUTING matrix is unverified, so
the watch app itself must schedule it.

Brutal verdict, as asked: a Path 1 watch app is glanceable-mirror-plus-
notification-haptics. Raise your wrist mid-rest and it shows the true
countdown (recomputed from the epoch anchor); log a set from the wrist while
the app is frontmost; get a rest-end haptic from a scheduled notification.
What it can NOT do: tick visibly wrist-down, run HR, or feel "live" the way
Hevy's does. Users who expect a workout-app watch experience would call the
gaps broken; users who want a remote button + wrist haptic get exactly that.
It is not nothing — but it is a companion remote, not a watch fitness app.

### Path 2 — WITH HKWorkoutSession
What it grants (evidence §2.1): true background runtime for the whole
session ("even when the user lowers their wrist"), high-frequency HR
samples generated by every session, one session at a time.

What it costs, exactly (evidence §2.2–2.3): the HealthKit entitlement; share
authorisation for workoutType (Apple's documented flow has no
authorisation-free session — a session-running app is a HealthKit-WRITING
app, unverified whether it technically starts without the request, and we do
not build on unverified); both NSHealth* purpose strings (watch extension
and, plausibly, the container app); the workout-processing background mode;
App Review 5.1.3 (health-data use/disclosure rules, "disclose the specific
health data") and 2.5.1 (intended-purpose) exposure. This is ROUTINE for
fitness apps in Apple review and materially different from the Google Play
Health Connect situation that drove the Android rip-out — but it re-opens a
surface this app deliberately closed to zero (evidence §2.4: no entitlement,
no strings, no health deps in today's builds), and the scope discipline must
be explicit: session runtime only, write nothing beyond the mandatory
workout type, read nothing, HR display optional and separately decided.
GDPR note: wrist HR shown live and discarded is one thing; persisting HR
into our EU-Dublin schema would be new Article 9 surface and is NOT in this
scope.

**The gate, plainly:** Path 2 is the only path that produces a watch app
users would recognise as working. Path 1 is shippable but will read as
limited next to Hevy. The decision is therefore really "accept the HealthKit
entitlement on iOS, scoped to session-runtime, or don't build a watch app
users expect". A middle route exists: ship Path 1's transport + UI first and
upgrade to Path 2 by adding the session object later — the SwiftUI app,
WatchConnectivity layer and phone-side commit path are identical in both.

## 2. ARCHITECTURE (phone-authoritative, already half-built)

The phone remains the single source of truth; the watch is a remote display
+ input. The repo is unusually ready for this (evidence §3):

- Rest timer state is one epoch-ms anchor (`restTimerEndsAt`) + duration —
  trivially serialisable; the watch renders its own countdown from the
  anchor and never owns time.
- The wrist-logged-set entry point ALREADY EXISTS and is test-pinned:
  `applyRemoteSetEvent` (COMP-020) — idempotent by eventId, recomputes set
  numbers phone-side, reuses the screen's primitives, defers PR celebration
  to the summary, persists the snapshot after apply. Precondition before
  any real watch traffic: fix SD-11 (the idempotency check spans an await;
  record the eventId synchronously before the DB write).
- Session snapshot (WK-1) already persists every mutation including
  `appliedRemoteEventIds`, so a set logged from the wrist while the phone
  app is backgrounded rides the existing draft/interruption machinery by
  construction — the watch sends events, never state.
- Transport: WatchConnectivity messages for live traffic (with
  `transferUserInfo` queuing for out-of-range/locked delivery — messages
  queue and deliver when the session next activates), App Group
  UserDefaults for the last-known snapshot so the watch can render
  something honest when the phone is unreachable. `WCSession.isReachable`
  requires the RN app running (evidence §4.3): the watch UI must therefore
  carry an explicit "open Volyume on your phone" state, not a spinner.
- Stale/conflict rules: events carry the workoutId; the phone rejects
  mismatches (already implemented); the watch treats every send as
  fire-and-acknowledge, re-sending unacknowledged events by eventId
  (idempotent by design).

## 3. EXPO/EAS REALITY CHECK (the riskiest unknown — verified)

This repo has NEVER shipped an extra Apple target: both local native modules
compile into the main target, and the Live Activity widget target was
specified but only materialised via the new `plugins/withVolyumeWidget.js`
config plugin (E6B) — which is exactly the proving run the watch needs,
and it has not yet been through an EAS iOS build (founder credential action
pending). Facts to price in (evidence §4):

- The community route is `@bacons/apple-targets` (4.0.7, May 2026), which
  supports `watch` targets, with the author's own word on EAS signing being
  "theoretically handled". A Feb-2026 issue (#175) reported broken watch
  embed/dependency wiring under Expo 54 prebuild; closed, fix status in
  4.0.7 UNVERIFIED — assume patch-package contingency.
- EAS multi-target credentials are official but still labelled
  experimental (`appExtensions` config); watch targets specifically carry a
  trail of provisioning failures (eas-cli #795, #2578). Assume first-build
  friction measured in days, not hours.
- A watch app adds at least one new bundle id (`app.volyume.watchkitapp`)
  with its own App ID and profiles — founder-side Apple Developer work,
  same class as the pending `app.volyume.widget` setup.
- Honest statement, as requested: adding the first genuinely separate app
  target meaningfully complicates every future iOS build — prebuild owns
  the Xcode project, so every target must be plugin-reproducible, and each
  EAS iOS build now signs and embeds two artefacts. The E6B widget target
  is the cheap dress rehearsal: if IT builds cleanly on EAS, the watch
  target rides a proven pipeline; if it doesn't, that friction is the
  watch's friction too, discovered at widget cost.

## 4. MINIMAL V1 (mirror how Hevy began — companion, not standalone)

Exactly this list, nothing else (evidence §5: Hevy's shipped v1 shape is a
paired companion; phone-free is the round-up's differentiator we defer):

1. Mirror the active session: current exercise name + target (reps range /
   weight) on the wrist, fed from the App Group snapshot + live messages.
2. Log a set from the wrist: one screen, prefilled from the phone's current
   set entry; sends the COMP-020 event; shows acknowledged/pending state.
3. Rest timer on the wrist: countdown from the anchor, wrist haptic at
   rest-end (Path 1: watch-scheduled notification; Path 2: in-session
   haptic), +15s and skip sending the existing adjust/stop events.

V2+ parking lot (explicitly OUT of v1): complications, standalone/phone-free
workouts, browsing routines or history, HR display and any HR persistence,
nutrition/macros on the wrist (the MacroFactor shape), Wear OS anything.

## 5. EFFORT + PHASING

Sizing, honestly: **XL — new platform.** SwiftUI app (3 screens + state
machine) + WatchConnectivity bridge module + phone-side bridge wiring +
plugin/EAS target work + a test strategy Jest cannot see: the JS seam
(`applyRemoteSetEvent`, serialisers) stays Jest-pinned; the Swift side gets
XCTest unit coverage in the target plus a founder device-walk matrix
(paired physical watch REQUIRED — whether the founder owns one is
unverified and is a blocking prerequisite to confirm).

Order of operations (each gate must pass before the next starts):
1. E6B widget target through a real EAS iOS build (already queued;
   founder credentials pending). This de-risks the entire plugin/EAS lane.
2. HealthKit gate decision (section 1). Everything downstream branches.
3. SD-11 fix + a serialiser module for the snapshot/event shapes (pure JS,
   Jest-covered, no watch needed).
4. Watch target via apple-targets (or an extension of our own plugin
   pattern), building an empty SwiftUI shell on EAS.
5. V1 features against the shell; founder device-walks with a paired watch.

Recommendation: commit to the sequencing above rather than a date; take the
HealthKit gate decision AFTER step 1 proves the pipeline (nothing about the
gate is needed sooner, and step-1 friction data will inform appetite).
Flip condition: if step 1 (the widget target) burns more than a week of
founder+build time on EAS provisioning, pause the watch plan entirely and
revisit after the Play/iOS release cadence stabilises — the same friction
would otherwise land on every future iOS release with a watch target
attached.

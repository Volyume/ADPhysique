## 2. BLOCKING design constraints from adversarial verification

Each CONFIRMED item must be designed out before any F5 code ships. The
proposed mitigations below are mine and need founder sign-off with the rest
of this plan.

**C1 (CONFIRMED) — Mixed-fleet tombstone resurrection.** Old builds' legacy
pulls select without a `deleted_at` filter, so the moment a new build writes
a tombstone, every old-build device resurrects the deleted row and can
re-push it. *Mitigation: two-phase cutover. Phase A (a normal app release,
no behaviour change): teach the LEGACY pull paths to filter/apply
`deleted_at` while writes remain hard deletes. Phase B (one or more releases
later, founder decides the gap): enable tombstone WRITES. No tombstone is
ever written while Phase A builds are not the effective floor of the fleet.*

**C2 (CONFIRMED) — Silent trigger refusal + clean-cycle watermark deadlock.**
The 047 touch-trigger pattern refuses stale writes SILENTLY (RETURN OLD, no
error), and a push watermark that only advances on a clean cycle would loop
forever on a permanently-refused row. *Mitigation: drop "refuse stale" from
the F5 triggers entirely — triggers only auto-bump updated_at when the
client failed to stamp it. Conflict resolution lives in the LWW-gated pull,
not in silent server rejections. Push watermarks advance past rows the
server acknowledged, full stop.*

**C3 (CONFIRMED) — Inherited pull watermarks skip pre-cutover edits.** The
legacy pulls already advance the same per-table watermark keys the new
handlers would read, past rows the OR-IGNORE applier never applied.
*Mitigation: each table's registry handler uses a NEW watermark namespace
(or resets to 0 on first registry cycle) and performs one full LWW-gated
re-pull at cutover — idempotent by construction, closes the skipped-edit
window.*

**C4 (CONFIRMED) — LWW defeated during the mixed-fleet window on plan
tables.** Old builds full-push programmes/routines every cycle re-stamping
updated_at=now, permanently overwriting newer edits from new builds.
*Mitigation: same two-phase discipline as C1 — Phase A ships honest
timestamps in the LEGACY push (stop re-stamping; a small, verifiable
change), Phase B flips the tables to the registry. Alternatively (founder
call) a minimum-supported-version bump makes the window finite.*

**P1 (PLAUSIBLE) — Article 9 flag on a clock race.** user_body_profile
carries gdpr/consent-adjacent flags; whole-row LWW puts them on a
last-clock-wins race. *Mitigation: per-column merge (the 045 pattern) for
user_body_profile; consent-class columns are never regressed by sync (a
true consent recorded anywhere wins; withdrawal is handled by its own
flow, never by row LWW).*

**P2 (PLAUSIBLE) — Sign-out-wipe guard gap in the registry path.**
*Mitigation: stage-1 scaffolding adds the isSignOutWiping guard + watermark
freeze to transport/handlers before any table migrates.*

**P3 (PLAUSIBLE) — Indefinite tombstones vs GDPR storage limitation.**
*Mitigation: commit to the 30-day server-side hard-delete job (founder-run
scheduled function) landing in the same stage as the first tombstone table;
"tombstones indefinitely" is withdrawn as an option.*

**P4 (PLAUSIBLE) — Article 9 gate lives only in runner.syncAll.**
*Mitigation: duplicate the fail-closed healthConsent check into
transport.pushTable before stage 1 (defence in depth; F2's invariant then
holds per-call, not per-cycle).*

The code-truth verifier returned "sound" overall: two plan claims were
refuted (weekly_checkins_v2 pull is ALREADY LWW-gated; library programme
rows ARE pushed today) and the database.js line citations carry a ~38-line

## 6. Risks (as synthesised)

- Timestamp-inflation deadlock at cutover (the top mechanical risk): years of legacy pushes re-stamped cloud updated_at = push-time (sync.js:782, 817), so cloud rows carry inflated timestamps. Once a touch trigger refuses stale writes AND the client starts sending honest (older) local updated_at, the first honest push of a genuinely-edited row can be refused as 'stale' against its own inflated cloud stamp — rows become permanently unpushable and the LWW pull then clobbers the local edit. Mitigation must be designed in: the 047 trigger pattern auto-bumps when the client omits updated_at — the migration wave needs either a one-off reconciliation pull-before-first-honest-push per table, or a trigger variant tolerant of the first honest write; test this exact scenario per table.
- Mixed-version fleet: until every device runs the new build, old builds keep full-pushing re-stamped rows through bulkUploadLocalData for tables the new build has migrated, re-inflating cloud timestamps and re-triggering conflict-by-push-order (SD-3) against new devices' honest stamps. Per-table staging shrinks but does not remove this window; the multi-device manual test matrix (mandate: 'highest-touch data change') must include one stale-build device.
- Delete-semantics flip on workouts (SD-9): converting hard deletes to tombstones changes what 'delete' means everywhere — local readers must filter deleted_at IS NULL or deleted workouts reappear in history/PB/stats; the 30-day server hard-delete job promised by the registry contract (registry.js:18-19) does not exist for these tables yet and unbounded tombstone growth on the largest table needs an answer.
- Founder-run migration sequencing: cloud migrations are manual and may lag builds (092/093/094 are STILL outstanding per CLAUDE.md status). The benign missing-TABLE skip (_missingTable.js) does NOT cover a missing TRIGGER or missing composite PK — a build shipped before migrate_098 is applied keeps 42P10-failing workout_notes pushes, and honest-timestamp code without its trigger silently reverts to trust-the-client LWW. Each stage must state its migration precondition and tolerate its absence explicitly.
- Pinned-test minefield: MIGRATED_TABLES is frozen (sync.transport.test.js:115), ordering pinned (migratedTablesOrder), legacy delegation pinned (sync.runner.triggers), bulkUploadLocalData export pinned (sync.publicApi), weekly_checkins_v2 pull pinned as INSERT OR IGNORE (sync.transport.test.js:413), and the regression matrix forces T1-T6 for every registry addition. Every stage deliberately updates specific pins; a 'fix the test to pass' reflex here would erase founder-locked contracts.
- Sign-out-wipe guard coverage regression: legacy pullFromCloud has 8 bailForWipe stages plus watermark-advance guards (sync.js:1262-1280); migrated tables rely instead on the runner's per-table pre-pull check (runner.js:214-221). Each table moved must not create a window where a long single-table pull writes into a wiping DB — and pullFromCloud.signOutGuard.test.js can only be retired at Stage 12, never mid-plan.
- ED-safety adjacency: user_body_profile (sex, scoff_score) and morning_weights (weight trend inputs) feed calorie floors, the rapid-loss gate, and edPatternDetector. A stale-clobber or resurrection bug in these two tables is not a data bug but a safety bug; CLAUDE.md requires stop-and-ask, tier-blind handling, and ED-safety cases in every device checklist for these stages.
- Watermark correctness at scale: per-table push watermarks are only safe when advancement is clean-cycle-only and boundary rows re-include (watermark.js:92-120 documents the immutable-rows caveat; foodDomain's minus-1-ms D-M1 pattern). Mutable tables (routines, programmes, coach_outputs) MUST use the food-domain discipline (strict > filter, minus-1-ms, advance only on zero failures) or edits made in the same millisecond as a push are skipped forever. New watermark keys must match the SD-1 excluded shapes or they will sync via user_prefs until Stage 11 (syncPrefExclusions pin).
- First-pull-after-migration load: adding tombstone-aware full pulls and fixing dead pulls (exercise_goals, planned_muscle_volume, workout_notes backlog) means the first cycle after several stages moves materially more data; fresh sign-in already full-pulls everything (self-healing cursors, watermark.js:13-23) — verify no PostgREST 1000-row-cap truncation on the newly-pulled tables (fetchByIdsChunked precedent).

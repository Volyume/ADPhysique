## What is genuinely good

- The connection state machine is complete and consistent client/server: `none` / `requested_by_me` / `requested_by_them` / `connected` map to one button shape each (`ConnectButton.js:92-97`), the 30-day re-request bar and `connect_from` refusals are named honestly (`connectRefusalLine`), and declining is genuinely silent end to end (no activity row written on decline, `migrate_161:1316-1321`).
- `trainingProfile.js` is a careful, well-isolated pure/IO split: `deriveTrainingProfile` takes an injected clock and reads nothing but timestamps, set rows and exercise ids, and `shareablePayload` builds the wire payload strictly from the toggle map so an un-named field can never travel (SD-30 is genuinely hard to violate by accident here).
- No percentages anywhere: the whole reasons vocabulary (client `CONNECT_REASONS`, server reason strings) is fixed wording with no numeric confidence score exposed, matching SD-24 exactly.
- Honest doors: `doorZeroState`/`doorLine` never fabricate a count, and a door that cannot work yet (`REQUIREMENT_ROUTE`) sends the person to the exact screen that unblocks it rather than hiding.
- Day-level timestamps only, everywhere messaging touches time: `ConversationRow`/`MessageBubble` both go through `postDayLabel`, and there is no clock-time string anywhere in the new files.
- Offline handling on the three new list-style screens (`CommunityPeopleListScreen`, `CommunityConversationsScreen`, `CommunityConversationScreen`) is real: each distinguishes `offline` from a generic failure and offers "Try again", not a spinner-forever or a false empty state.
- `_community_message_json`'s ref resolution is safety-conscious: it re-checks `_community_can_view_programme`/`_community_can_view_post` for the CURRENT viewer before attaching a tile, so a reference to a programme or post that has since gone private renders as text only rather than leaking a title (migrate_161:752-759).
- No em dashes, no internal terms ("band", "RPC", "cursor") leaked into any user-facing string across the reviewed files.

---

## Verdict

**Do not merge as-is.** Two P0s are real gaps against the founder's own device
checklist and the minor-safety rule this campaign exists to keep: messaging
from the programme screen (checklist item 20) is simply not built, and the
partner section actively misleads an under-18 account rather than being
hidden from them. The P1s are all in the "the code claims something it does
not honour" family the review was asked to hunt for: a reference tile that
never shows who it is from, a rules-acceptance refusal that lies about being
an offline problem on two of three surfaces, and a profile screen that offers
two routes each to two different actions. Fix 1-5, re-walk journeys 5 (message
from a programme), 8 (minor) and 9 (rules_outdated on training profile), and
this is close: the connection/messaging architecture, the reasons vocabulary
and the day-level-only timestamp discipline are all sound.

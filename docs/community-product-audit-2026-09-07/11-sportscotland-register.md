## 1. Schema

All three layers were loaded and every feature's `properties` key set was
checked for consistency (one distinct key set per layer — no drift within
a layer). Geometry is `Point`, and the FeatureCollection `crs` on every
layer is declared `urn:ogc:def:crs:EPSG::4326` — **the `geometry.coordinates`
values are already WGS84 lon/lat**, confirmed by inspection (e.g. the first
`pub_spffs` feature sits at `[-2.0895, 57.1089]`, correctly on Aberdeen).
This means the register needs **no OSGB/Irish-Grid conversion**, unlike the
NI (Irish Grid TM75) and Wales (OSGB36, mislabelled as WGS84 in the
acquisition doc) adapters. The `eastings_x`/`northing_y` (or `x`/`y`)
properties are the OSGB National Grid reference and are redundant once the
geometry is used.

| Layer | Properties (exact key set, no variation found) | Count |
|---|---|---|
| `pub_spffs` (fitness suites) | `sh_date_uploaded`, `site_name`, `address`, `postcode`, `la_name`, `town`, `eastings_x`, `northing_y`, `facility_sub_type`, `fid` | 629 |
| `pub_spfsh` (sports halls) | `sh_date_uploaded`, `site_name`, `address`, `postcode`, `la_name`, `town`, `fid`, `x`, `y`, `fac_sub_type` | 3,129 |
| `pub_spfsp` (swimming pools) | `sh_date_uploaded`, `site_name`, `address`, `la_name`, `town`, `eastings_x`, `northing_y`, `fid`, `fac_sub_type` | 562 |

Notable, evidence-based, not assumed:
- **The field name for the facility sub-type is not consistent across
  layers**: `facility_sub_type` on `pub_spffs`, `fac_sub_type` on the other
  two. An adapter reading all three must not assume one key name.
- **`pub_spfsp` (pools) has no `postcode` property at all** — not null,
  absent from every one of its 562 features' key sets. `pub_spffs` is
  missing postcode on 1 of 629 rows; `pub_spfsh` on 25 of 3,129.
- **`sh_date_uploaded` is a single value across the entire register**:
  `2024-07-24` on all 4,320 features, all three layers. This is a single
  snapshot/export date, not a rolling per-record update timestamp — treat
  the whole register as one dated extract, not as a per-row freshness
  signal.
- **No ownership/operator field.** No column names an operator, chain, or
  managing trust anywhere in any of the three layers — only `la_name` (the
  *local authority area* the site sits in, not who runs it — e.g. a
  Bannatyne's or David Lloyd site inside a hotel still carries the council
  area as `la_name`, confirmed against sample rows above).
- **No per-site id.** `fid` is unique within a layer (checked: zero
  duplicate `fid` values inside `pub_spffs`, `pub_spfsh`, or `pub_spfsp`
  individually) but is **reused across layers** — `fid=1` exists
  independently in all three files, so `fid` alone cannot key a cross-layer
  join and there is no field anywhere that identifies "this fitness suite
  and this sports hall are the same physical site" other than name/
  address/postcode/coordinate matching (which is exactly what GD-04 asks
  for, done in Section 2 below).

## 2. Collapsing facilities to SITES (GD-04)

GD-04: "One canonical row per physical venue. Active Places facilities
collapse to their site; a site with several countable fitness facilities is
one venue with `facility_count`." The register has no cross-layer site id
(Section 1), so the collapse has to be done the same way GD-06 blocks
candidate pairs: by folded name plus postcode, backstopped by proximity.

**Method used** (script: `<scratchpad>/work/analyze.py`, union-find over
all 4,320 facilities from all three layers): two facilities are grouped
into the same site when their `site_name` folds to the same token string
(the same `foldText`/`tokenize` used by `lib/fold.js`) **and** either (a)
they share the same normalised postcode unit, or (b) they are within 100 m
by haversine distance on the WGS84 geometry. Condition (b) is what lets a
`pub_spfsp` pool feature (no postcode field at all) still join a
`pub_spffs`/`pub_spfsh` feature at the same site.

```
[merge reasons] Counter({'same_name_same_postcode': 2443, 'same_name_within_100m': 1262})
[sites] total distinct sites=2463
```

Result: **4,320 facilities collapse to 2,463 distinct sites.**

| Site population | Count |
|---|---|
| **Sites carrying a fitness suite (`pub_spffs`) — the core set** | **573** |
| Sites with a sports hall and/or pool but **no** fitness suite (context only) | 1,890 |
| ...of which sports-hall only | 1,718 |
| ...of which pool only | 97 |
| ...of which sports hall **and** pool, still no fitness suite | 75 |

629 raw `pub_spffs` features collapse to 573 sites because a handful of
sites carry more than one fitness-suite facility row (e.g. a separate
"Weights" row and a separate "Weights And CV" row at the same site) — this
is exactly the GD-04 `facility_count` case, not a duplicate.

**Caveat on the method (evidence, not certainty):** the collapse rule is my
own re-implementation for this analysis, not a rule quoted from the
blueprint verbatim — GD-04 states the *requirement* ("one row per site")
but not the exact join predicate for this specific register. I chose
name-fold + (postcode-or-100m) because it mirrors GD-06's own blocking
strategy and the register's own field gaps (pools carry no postcode). A
different join rule (e.g. address-line equality instead of/alongside name)
would shift the 2,463/573 counts slightly; the order of magnitude will not
move because 2,443 of the 2,463 unions fired on the strict
name+postcode match, with 100 m proximity only picking up the remainder.

## 3. Gap analysis against the current catalogue

**Catalogue load:** `data/gyms/uk-gyms.v1.jsonl.gz` decompressed to scratch
(46,817 rows). Scottish rows selected by `country == 'Scotland'` (3,169
rows) **plus** 8 rows with `country: null` whose postcode falls in a
Scottish postcode area (AB/DD/DG/EH/FK/G/HS/IV/KA/KW/KY/ML/PA/PH/TD/ZE) —
**3,177 Scottish catalogue rows total**, all compared.

**Scoring** (re-implemented in Python from `scripts/gyms/lib/dedupe.js`,
restricted to the three signals the register can actually supply — it has
no phone, no website, and no brand field, so `same_brand`/`same_phone`/
`same_website_host` never fire for a register-side record and are
correctly omitted rather than silently scored as false-negative zeros):

- same postcode unit (both normalised per `lib/postcode.js`): **+2**
- name token Jaccard, folded, town-token-excluded per GD-22
  (`nameTokensExcludingTown`), single-token guard applied exactly as in
  `lib/dedupe.js` (neither side scores name points if either side reduces
  to ≤1 token after removing its own town's tokens): **0.85+ → +3**,
  **0.6–0.85 → +1**
- within 100 m haversine: **+2**; within 150 m: **+1**

Decision thresholds, exactly as GD-06/`MERGE_THRESHOLD`/`REVIEW_THRESHOLD`
in `lib/dedupe.js`: **merge ≥ 5, hold/review 3–4, distinct < 3.** For each
of the 573 fitness-suite sites, every one of the 3,177 Scottish catalogue
rows was scored and the single best-scoring catalogue row was kept
(brute-force, 573 × 3,177 ≈ 1.8M comparisons — no blocking needed at this
scale).

```
[dedupe] fitness sites=573 merge=30 review=129 distinct=414
```

| Band | Sites | Share of 573 |
|---|---|---|
| **Merge** (score ≥ 5 — already in the catalogue) | 30 | 5.2% |
| **Hold / review** (score 3–4) | 129 | 22.5% |
| **Distinct** (score < 3 — not in the catalogue) | 414 | 72.3% |

**Headline finding: only 30 of the 573 register fitness-suite sites
(5.2%) already have a confident match in the catalogue.** The catalogue's
Scottish coverage does not currently draw on any authoritative Scottish
facilities register — its source_records for Scottish rows are
`active_places` (Sport England's *English* Active Places Power dataset,
confirmed by `source_name: "Sport England Active Places Power"` on sampled
rows — it has no Scottish jurisdiction), `overture`, `operator:*`,
`companies_house`, none of which is sportscotland. This is direct
confirmation of the gap GD-02 already named ("sportscotland ... once the
founder's free account exists" — i.e. not yet wired in).

**A specific false-positive risk this scoring surfaced, worth flagging
before any of this feeds an adapter:** two entirely different "X Leisure
Centre" sites in different towns (e.g. `Balmedie Leisure Centre` vs
catalogue's `Troon Leisure Centre`) score a full `name_jaccard_high:+3`
once each side's own town token is stripped from its name (GD-22) — because
both fold to the same two-token `["leisure","centre"]` set. This is the
*shipped* dedupe.js behaviour, faithfully reproduced here, and in this
case it did no harm: with no postcode or proximity corroboration the pair
lands at score 3 (hold), never auto-merges. It is a known soft spot of
GD-22's town-token stripping specifically for generic "Leisure
Centre"/"Sports Centre" names and is worth the pipeline owner's awareness,
not a defect introduced by this analysis.

**Classification method and its limits (evidence, not a clean taxonomy):**
a site is tagged `hotel` if "hotel" appears in its folded name; `university`
if "university" appears; `school_or_academy` if "school"/"academy"/
"primary"/"high"/"grammar" appears; `council_leisure_centre` if "council"
or a "leisure/sports centre" bigram appears in the name; `community_centre`
if "community" and "centre" both appear; `private_or_independent_gym` if a
generic gym/fitness/club token appears with no council/leisure signal;
everything else is `other`. This is a first-pass name heuristic, not a
brand-list lookup — it under-classifies real chains that don't carry a
generic token in their own name. Confirmed example in the `other` bucket:
**"Bannatyne's Aberdeen"** is a known commercial health-club chain
(`Bannatyne Perth` is even in the merge band above, matched to a *different*
register site) but has neither "gym" nor "club" in its own name, so the
heuristic places it in `other` rather than `private_or_independent_gym`.
A real adapter should classify against GD-05's brand/alias table, not name
tokens alone — Section 5 recommends this explicitly. The 110-row `other`
bucket also contains golf clubs, rugby/cricket/hockey clubs, and youth
clubs with an on-site fitness suite (`Alloa Rugby Football Club`,
`Dullatur Golf Club`, `Currie Youth Club` — visible in the "Private or
independent gym" and "Other" tables below) — these are membership-
restricted sports clubs, not public gyms, and are a candidate for GD-03
`excluded` or `other_fitness` rather than a core gym type; this is flagged
as an open question in Section 5/Ambiguities, not resolved here.

## 5. Recommendation (evidence only — no adapter written)

### Which layers feed the pipeline

- **`pub_spffs` (fitness suites) is the canonical gym-type source layer.**
  It is the only layer that identifies "this site has a countable fitness
  facility" — the thing GD-01/GD-04 actually need. 573 sites, 72.3% of
  them (414) entirely new to the catalogue's Scottish coverage (Section
  3c) — this is real, material lift, not noise.
- **`pub_spfsh` (sports halls) and `pub_spfsp` (swimming pools) are
  corroboration only, never a standalone gym-type source.** 1,890 sites
  carry a hall and/or pool with no fitness suite at all (Section 2) — a
  school sports hall or a council swimming pool with no gym is not a gym,
  and GD-03's core types plus `excluded` give no slot for "sports hall,
  no fitness offering" as a primary venue. Where a hall/pool feature sits
  at the *same site* as a fitness suite (already true for every one of the
  573 core sites, since GD-04 collapses them), it should attach as
  additional evidence/amenity metadata on that site's row (informs
  `facility_count` and could inform a future "has swimming pool" /
  "has sports hall" amenity flag), not spawn a second venue.

### `venue_type` mapping, evidence-based, per sub_type and name pattern

GD-03's priority order is operator brand type > VOA description/special
category > Active Places facility/ownership > NI ownership/flags > name
tokens (last resort). The register has none of the first four signals
(Section 1: no operator field) — so **every register-sourced row is
necessarily classified on the GD-03 "last resort" tier**, unless
`classify.mjs`'s existing `matchBrand`/brand-alias lookup (already run
against every source's `name` in `normalise.mjs`, confirmed reading that
file) independently recognises a chain name in `site_name` first (this
already happens correctly for the merge-band rows above — e.g. `Anytime
Fitness`, `David Lloyd`, `Fitness First` — because brand matching runs on
the cleaned name regardless of source).

For whatever remains unmatched by brand, evidence from Section 3
motivates this name/sub_type-pattern mapping:

| Pattern (folded name contains, or context) | Recommended `venue_type` | Evidence |
|---|---|---|
| Brand-matched via existing `lib/brands.js` alias table | brand's own type (`commercial_gym`/`health_club`/etc.) | 30 merge-band rows already prove this path works |
| `hotel` in name | `hotel_gym` | 42 raw facilities / 32 not-in-catalogue sites (Section 4) |
| `university` in name | `university_gym` | 4 sites (Section 3c) |
| `council` in name, or a "leisure centre"/"sports centre" bigram, **and** the site has a fitness suite | `leisure_centre` | 51 sites classified this way in Section 3c; matches GD-03's explicit "a leisure centre with a fitness suite is a core venue" |
| `school`/`academy`/`primary`/`high`/`grammar` in name | **open question, not `excluded` by default** — see Ambiguities | 171 sites, the largest single bucket |
| `community centre`/`community` + `centre` in name | `leisure_centre` if genuinely public-access, else `other_fitness` | 11 sites |
| Golf/rugby/cricket/hockey/youth club, no council/leisure signal | `other_fitness` (membership-restricted) or `excluded`, founder/GD-03 call | ~15–20 of the 35 "private_or_independent_gym"-bucketed rows are actually member clubs, not open gyms (e.g. `Alloa Rugby Football Club`, `Dullatur Golf Club`) |
| Remaining generic gym/fitness/club name, no council/leisure/hotel/uni/school signal | `independent_gym` | remainder of the 35 + relevant part of the 110 `other` |

**The school question is the single largest open item.** 171 of 414
distinct sites (41%) are school-housed. GD-03 says `excluded` covers
"school-only sites" (closed access) but this register is explicitly
sportscotland's **public** facilities register (`pub_` prefix on every
layer name) — meaning sportscotland itself lists these as public/
community-accessible dual-use facilities (evening/weekend community
lets are standard practice for Scottish school sports facilities), not
closed-access school property. Treating all 171 as `excluded` would
silently drop 30% of the entire not-in-catalogue fitness-suite gap;
treating all 171 as `leisure_centre` risks surfacing genuinely
closed-access school gyms to users who can never book them. This needs a
founder/GD-03 ruling before an adapter runs — see Ambiguities.

### Adapter contract

The pipeline's contract, read directly from the two adapters that exist
and from `scripts/gyms/normalise.mjs` (never inferred):

**Wiring.** `normalise.mjs` holds a `PRIMARY_SOURCES` array of module
names and dynamically imports each as `./sources/${moduleName}.mjs`,
calling `mod.readRecords(RAW_DIR, log)`:
```js
const PRIMARY_SOURCES = ['active-places', 'active-places-ni', 'datamap-wales', 'operators', 'overture', 'voa'];
...
for (const moduleName of PRIMARY_SOURCES) {
  const mod = await import(`./sources/${moduleName}.mjs`);
  for await (const rec of mod.readRecords(RAW_DIR, log)) { ... }
}
```
A `sportscotland` adapter would be `scripts/gyms/sources/sportscotland.mjs`
added to that array.

**Input.** `RAW_DIR = process.env.RAW_DIR || process.argv[2] || DEFAULT_RAW_DIR`
(same pattern in every one of `normalise.mjs`/`build.mjs`/`geocode.mjs`/
`audit.mjs`). Each adapter resolves its own file(s) under `rawDir` by a
fixed relative path it owns, e.g. NI's `const NI_FILE = 'ni/active-places-ni.csv'`
and Wales's `const WALES_FILE = 'wales/leisure-centres-wales.geojson'`. A
sportscotland adapter would define its own three relative paths, e.g.
`scotland/pub_spffs.geojson`, `scotland/pub_spfsh.geojson`,
`scotland/pub_spfsp.geojson` under `RAW_DIR`, and (per the founder's "no
authkey in any URL/report" instruction and this task's ban on network
calls) would read the **already-fetched, key-stripped** GeoJSON files from
disk exactly like NI/Wales read their pre-fetched CSV/GeoJSON — it does not
call the WFS endpoint itself.

`ni`/`wales` above, should carry what the register uniquely offers and
nothing else does: `{ la_name, layer: 'fs'|'sh'|'sp', sub_type,
sh_date_uploaded }` — `la_name` because GD-08's location hierarchy is meant
to come from ONSPD via postcode, not from the source, but `la_name` is
useful corroboration/fallback exactly where a postcode is missing (all of
`pub_spfsp`, 1 of `pub_spffs`, 25 of `pub_spfsh`); `layer` and `sub_type`
because `facility_sub_type` (fitness suites) and `fac_sub_type` (halls/
pools) are the only place the register records what kind of facility this
is, needed for the `facility_count`/amenity logic in Section 5's mapping
table above; `sh_date_uploaded` because it is the register's one dating
signal (Section 1), even though it is a single constant across the whole
2024-07-24 export rather than a per-row value.

satisfied, exactly as NI and Wales each already collapse to one row per

## Ambiguities / could not determine

1. **School-housed fitness suites (171 of 414 distinct sites, the largest
   single bucket) — `excluded` vs `leisure_centre`/`other_fitness`.** GD-03
   excludes "school-only sites" but this register is sportscotland's
   *public* facilities list, meaning these are presumptively community-
   accessible. Cannot determine from the register alone which named sites
   are genuinely open to the public (evening/weekend community lets) vs
   which are misfiled/aspirational entries with no real public access —
   the register carries no access/opening-hours field. Needs a founder/
   GD-03 ruling before an adapter runs; this analysis deliberately did not
   pre-decide it (Section 4/point 6 of CLAUDE.md — a genuine product/data
   fork).
2. **Membership-restricted sports clubs (golf/rugby/cricket/hockey/youth
   clubs with an on-site fitness suite, ~15–20 rows inside the "private or
   independent gym"/"other" buckets)** — GD-03 has no explicit ruling on
   whether a fitness suite gated behind sports-club membership counts as
   `independent_gym`, `other_fitness`, or `excluded`. Flagged, not
   resolved.
3. **The GD-04 site-collapse join predicate is this analysis's own choice**
   (Section 2), not a rule quoted from the blueprint verbatim — GD-04
   states the requirement, not the exact algorithm for this register. A
   different join rule would shift the 2,463/573 counts by some margin;
   the qualitative finding (roughly 570 fitness-suite sites, ~72% new to
   the catalogue) is robust to reasonable variations because 99.6% of the
   unions fired on strict name+postcode equality, not the 100 m fallback.
4. **The 22 uncorroborated catalogue "leisure_centre"/council-like rows**
   (Section 3d) — cannot determine from available evidence how many are
   genuinely missing from the sportscotland register (i.e. real venues the
   register simply doesn't carry, e.g. very new or very small facilities)
   versus scrape/naming defects in the catalogue's own Overture-sourced
   rows. Both possibilities are evidenced (some names look like clean real
   venues, e.g. `Blairhall Community Leisure Centre`; others are visibly
   corrupted, e.g. `"Scotstoun Leisure Centre\Fitness centre"`).
5. **Whether `pub_spfsh`/`pub_spfsp`-only sites (1,890) should ever surface
   in the app at all**, even as corroboration metadata invisible to the
   core gym search — no requirement in GD-01 through GD-14 covers a
   "leisure centre with no gym" venue type, and this analysis was scoped
   to gap-analyse the fitness-suite core set, not to design that surface.
6. **Coordinate accuracy has not been spot-checked against a ground-truth
   source** — 100% of features carry WGS84 coordinates and the CRS
   declaration is internally consistent (sampled points land in the
   correct town), but no independent verification (e.g. against ONSPD
   postcode centroids) was run in this pass.

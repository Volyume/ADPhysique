## A. People search

**Client:** `src/screens/CommunitySearchScreen.js`. One `SearchBar` (line
152), two tabs (`People` / `Programmes`, lines 162-163). Debounce
**250 ms** (`DEBOUNCE_MS`, line 36) via `setTimeout` in a `useEffect`
(lines 107-110). A monotonic `seqRef` guards against a slow earlier answer
overwriting a newer one (lines 58-60, 73, 81, 86) — same pattern as the
food search per the file's own header comment.

**Lib:** `src/lib/community/feed.js` `searchPeople(q, {limit=20})` (lines
158-163) → `callCommunity('community_search_people', {_q: q.trim(), _limit})`.
No client-side minimum-length gate: `CommunitySearchScreen.run()` (line 65)
only skips the call when the trimmed query is **empty**, not merely short —
a 1-character query IS sent to the server.

**RPC:** `community_search_people(_q text, _limit int DEFAULT 20)`
(`supabase/migrate_160_community.sql:2941-2977`):

```sql
IF v_q IS NULL OR length(v_q) < 2 THEN
  RETURN jsonb_build_object('people', '[]'::jsonb);
END IF;

SELECT coalesce(jsonb_agg(public._community_profile_card(p.user_id, v_uid)
         ORDER BY (p.handle LIKE v_q || '%') DESC, p.last_active_at DESC), '[]'::jsonb)
INTO v_out
FROM (
  SELECT pr.user_id, pr.handle, pr.last_active_at
  FROM public.community_profiles pr
  WHERE pr.status = 'active'
    AND pr.visibility = 'public'
    AND pr.is_minor = false
    AND pr.user_id <> v_uid
    AND NOT public._community_is_blocked(v_uid, pr.user_id)
    AND (
      pr.handle LIKE v_q || '%'
      OR ' ' || public._community_fold(pr.display_name) LIKE '% ' || v_q || '%'
    )
  ORDER BY (pr.handle LIKE v_q || '%') DESC, pr.last_active_at DESC
  LIMIT v_lim
) p;
```

**Exact semantics:**
- **Server-side minimum length: 2** characters of *folded* text
  (`v_q := nullif(public._community_fold(_q), '')`, then `length(v_q) < 2`
  short-circuits to `[]`). A 1-character search always returns empty,
  regardless of what the client sent.
- **Match type — handle:** `LIKE v_q || '%'` = **prefix**, case-sensitive on
  the raw comparison but `v_q` itself is folded (lowercased, accents
  stripped) while `p.handle` is stored lower-case already (handles are
  `lower(btrim(...))` at write time, `migrate_160:1499` /
  `_community_handle_valid`), so effectively case-insensitive prefix match
  on handle.
- **Match type — display name:** `' ' || fold(display_name) LIKE '% ' || v_q || '%'`
  = **prefix-of-word** (any whitespace-delimited word in the folded display
  name may start with the query), not a full substring match. The code
  comment (line 2967-2969) is explicit: *"sam" finds "Big Sam" but not
  "Awesome"* — i.e. "sam" would NOT match if it were mid-word ("Awesome"
  contains "some" not "sam" as a word start, so this is consistent, but the
  general rule is: only word-initial substrings match, not arbitrary
  substrings).
- **Diacritics/case:** handled by `_community_fold` (`migrate_160:686-717`):
  lowercases, strips a fixed Latin accent table (à→a, ü→u, etc., plus
  æ→ae, œ→oe, ß→ss), replaces all non-alphanumeric with a space, collapses
  whitespace. No Unicode normalisation call — a fixed translation table,
  documented as deliberately matching the client's `foldText()` in
  `src/lib/community/keywordFilter.js` character-for-character. Non-Latin
  scripts (Cyrillic, CJK, Arabic) are **not folded at all** — they pass
  through `lower()` only.
- **No trigram/fuzzy/typo tolerance whatsoever** in people search. It is a
  plain `LIKE` prefix match. (Typo tolerance exists ONLY in the gym search
  ranker, `src/lib/gyms/rank.js`, Levenshtein-based — see section F. People
  search has none.)
- **Ranking:** exact-handle-prefix-match first (`(handle LIKE q||'%') DESC`),
  then `last_active_at DESC`. No popularity, no follower count, no
  relevance score.
- **Limit:** `_community_limit(_limit)` (`migrate_160:996-1006`, not shown
  in full but referenced everywhere) clamps to a fixed max; client sends
  `limit: 20` (`PAGE`, `CommunitySearchScreen.js:37`).
- **Pagination: NONE for people search.** `searchPeople`'s wrapper
  (`feed.js:158-163`) reads `data.people` only; `listPage()` (line 65-71)
  does read a `cursor` key off the payload, but `community_search_people`'s
  `RETURN` (line 2976) is `jsonb_build_object('people', v_out)` — **no
  `cursor` key at all**. `CommunitySearchScreen.loadMore()` (line 90) is
  explicitly gated `if (tab !== 'programmes' ...) return` — people search
  is a single page, hard-capped at `_limit` (20), full stop. A person
  cannot page past the first 20 name matches.
- **"No results":** `CommunitySearchScreen.js` lines 129-133 — icon
  `people-outline`, title *"No one by that name yet"*, text *"Try the start
  of their handle, or their display name."* (an honest hint that only
  prefix matching works).
- **Exclusions:** `status = 'active'` (excludes `restricted` AND
  `suspended`), `visibility = 'public'` (excludes followers-only profiles
  entirely — a followers-only person is **never findable by search**, only
  by direct profile link or being already followed), `is_minor = false`
  (a minor's profile is unconditionally excluded from search, independent
  of visibility), `NOT _community_is_blocked` (symmetric, either
  direction). **Muted people are NOT excluded** — grep confirms
  `community_mutes` is read only by `community_feed`/
  `community_discover_posts` (post-author filtering,
  `migrate_160_community.sql:2657-2658`, `2716-2717`) and by
  `_community_profile_card`'s own `relationship.muted` flag; search, find
  people and suggestions never consult it. Muting a person hides their
  *posts* from the feed; it does nothing to their discoverability.
- **Recent searches: do not exist.** No `recentSearch`/search-history
  string anywhere in `CommunitySearchScreen.js` or `src/lib/community/*`.
  Every open is a blank field.

**Programmes tab** (`searchProgrammes`, `feed.js:166-170` →
`community_search_programmes`, `migrate_160:2397-2470`, not reproduced in
full here as out of the "people" scope of A, but structurally: title match,
paginated via the real cursor, unlike people).

## B. Find people / doors

**Client:** `src/screens/CommunityFindPeopleScreen.js`. Six fixed doors,
defined in `src/lib/community/findPeople.js:35-82`
(`FIND_MODES`/`FIND_MODE_ORDER`), in this exact order:

| # | mode | label | `requires` (own-profile field) | requirement copy when missing |
|---|------|-------|---------------------------------|--------------------------------|
| 1 | `gym` | At my gym | `gym_label` | "Add your gym to see who trains there" |
| 2 | `area` | Near me | `area_label` | "Add your area to see who trains near you" |
| 3 | `like_me` | Train like me | none | — |
| 4 | `programme` | On my programme | `tp_programme_key` | "Set an active plan to see who else is on it" |
| 5 | `partners` | Open to training together | none | — |
| 6 | `might_know` | People you might know | none | — |

**Reachability of each door:**
- `gym`/`area`: value comes from the caller's **own free-choice profile
  fields**, entered on `CommunityEditProfileScreen` — `gym_label` via the
  `GymPicker` component wired to a real gym-directory venue (`gym_id`) or,
  for legacy profiles, still free text; `area_label` via a plain
  `TextInput` (`CommunityEditProfileScreen.js:289`, 40-char cap,
  `_community_clean_text` filtered, folded to `area_key`). A door whose
  `available` is `false` (`findPeople.js:104-118`) routes on tap to
  `CommunityEditProfile` (`REQUIREMENT_ROUTE`, `CommunityFindPeopleScreen.js:54-58`).
- `programme`: value is `tp_programme_key`, set from the person's own
  active local plan (`trainingProfile.js:programmeKeyFor`, lines 426-450) —
  not user-typed, derived from what plan is currently active.
  Unavailable → routes to `CommunityTrainingProfile`.
- `partners`: gated by `open_to_partner` boolean (a toggle, "Open to
  training together"), not a "requires" field — `available` is always
  `true` structurally (`requires: null`) but the RPC itself returns an
  empty, honest zero-count page when the flag is off (see RPC body below).
- `like_me`/`might_know`: always available, no precondition.

**Doors do NOT combine.** `community_find_people(_mode text, _cursor,
_limit)` takes exactly one `_mode` (`migrate_161:1821`/`migrate_162:2120`,
identical signature). There is no gym+days+goal composite call anywhere in
the client or server: `CommunityFindPeopleScreen.openDoor()`
(lines 159-168) navigates to `CommunityPeopleListScreen` with a single
`{mode, key, label}`; the screen calls `findPeople(mode, ...)` with that one
mode and nothing else. A user cannot ask for "at my gym AND partner-open".
The six doors are **mutually exclusive filters**, each internally combined
with a **fixed, non-configurable** set of *scoring* signals (below) — the
scoring signals are never exposed as user-selectable filters at all.

**Exact SQL — the current, superseding body is `migrate_162_gym_directory.sql:2120-2378`**
(re-issued over `migrate_161`'s `1821-2104` with one addition, lead
addition (b): the 'gym' hard filter widens to also match a person whose
`other_gym_ids` contains the viewer's `gym_id`). Reproduced verbatim
(migrate_162 version, current):

**HARD FILTERS** (row-selection WHERE clause, applies to every mode):
```sql
WHERE p.status = 'active'
  AND p.visibility = 'public'
  AND p.is_minor = false
  AND p.user_id <> v_uid
  AND NOT public._community_is_blocked(v_uid, p.user_id)
  AND NOT public._community_is_connected(v_uid, p.user_id)
  AND (_mode <> 'gym'       OR p.gym_key = v_key
         OR (v_me.gym_id IS NOT NULL AND v_me.gym_id = ANY (p.other_gym_ids)))
  AND (_mode <> 'area'      OR p.area_key = v_key)
  AND (_mode <> 'programme' OR (p.tp_programme_key = v_key AND p.show_programmes = true))
  AND (_mode <> 'partners'  OR p.open_to_partner = true)
  AND (_mode <> 'partners'
       OR NOT coalesce((p.partner_prefs ->> 'same_gym_only')::boolean, false)
       OR (v_me.gym_key IS NOT NULL AND p.gym_key = v_me.gym_key))
ORDER BY p.last_active_at DESC
LIMIT 300
```
Note: `like_me` and `might_know` add **no** mode-specific hard filter — every
active/public/non-minor/unblocked/unconnected candidate (up to 300, ordered
by recent activity) is scanned and scored; a candidate is only *kept* if its
score is `>= 1` for these two modes (see below). `gym`/`area`/`programme`/
`partners` keep every matching candidate regardless of score.

**RANKING / SCORING** (per-candidate, additive; applies identically across
all six modes — this is the "reasons" system):

```sql
IF v_me.gym_key IS NOT NULL AND v_row.gym_key = v_me.gym_key THEN
  v_score := v_score + 3;  reasons += 'Trains at <gym_label>'
ELSIF v_me.gym_id IS NOT NULL AND v_me.gym_id = ANY (v_row.other_gym_ids) THEN
  v_score := v_score + 2;  reasons += 'Also trains at your gym'
END IF;

IF v_me.tp_programme_key = v_row.tp_programme_key (both not null) THEN
  v_score += 3;  reasons += 'On the same programme'
END IF;

IF shared style (v_me.styles ∩ v_row.styles, first match) THEN
  v_score += 2;  reasons += 'Also trains <style label>'
END IF;

IF v_me.area_key = v_row.area_key (both not null) THEN
  v_score += 2;  reasons += 'Lists <area_label>'
END IF;

-- mutual CONNECTIONS (community_connections, state='connected'):
v_mconn := count of shared connected users;
IF v_mconn > 0 THEN v_score += least(v_mconn*2, 3);  reasons += 'Connected to N of your connections'

-- mutual FOLLOWS (both accepted):
v_mfoll := count of shared accepted-follow targets;
IF v_mfoll > 0 THEN v_score += least(v_mfoll, 3);  reasons += 'Followed by N you follow'

IF v_me.goal = v_row.goal (both not null) THEN v_score += 1;  reasons += 'Same goal'

-- shared time band (both chose to share tp_time_bands):
IF overlap THEN v_score += 2;  reasons += 'Both usually train <time band phrase>'

-- shared days, needs >= 2 days in common:
IF |days ∩| >= 2 THEN v_score += 1;  reasons += 'Both train <day list>'

IF tp_sessions_band equal (both not null) THEN v_score += 1;  reasons += 'Both train <sessions phrase> times a week'

IF tp_experience_band equal (both not null) THEN v_score += 1;  reasons += 'Similar experience'

-- staple lifts intersection, capped 3:
v_lifts := |staples ∩|; IF v_lifts > 0 THEN v_score += least(v_lifts,3);
  reasons += '<n> staple lift(s) in common'

IF both open_to_partner THEN v_score += 2;  reasons += 'Both open to training together'
```

**Full reason-chip vocabulary for `community_find_people`** (fixed strings,
never a percentage — SD-24):
1. `Trains at <gym_label>` (weight 3)
2. `Also trains at your gym` (weight 2 — other_gym_ids cross-match, migrate_162 lead addition (b))
3. `On the same programme` (weight 3)
4. `Also trains <style label>` (weight 2)
5. `Lists <area_label>` (weight 2)
6. `Connected to <n> of your connections` (weight `least(2n,3)`)
7. `Followed by <n> you follow` (weight `least(n,3)`)
8. `Same goal` (weight 1)
9. `Both usually train <mornings|at midday|in the afternoon|evenings|late>` (weight 2)
10. `Both train <day list, e.g. "Mon, Wed and Fri">` (weight 1, needs ≥2 shared days)
11. `Both train <1 to 2|3|4 to 5|6 or more> times a week` (weight 1)
12. `Similar experience` (weight 1)
13. `<n> staple lift(s) in common` (weight `least(n,3)`, singular/plural handled)
14. `Both open to training together` (weight 2)

**Ties:** broken by `last_active_at DESC` (`ORDER BY score DESC,
last_active_at DESC`, both in the paging query and unchanged from
`migrate_161`).

**Pagination:** cursor is a **plain zero-based offset encoded as a decimal
string**, not a keyset. `_cursor` is validated `^[0-9]{1,6}$`
(`migrate_161/162:1858-1862`/`2158-2162`), used as `OFFSET v_off LIMIT
v_lim` over the **already-materialised, already-scored, in-memory array**
(`v_items`, built by looping over up to 300 rows in PL/pgSQL then unnested
and re-sorted). This means: (a) the scan is capped at 300 candidates total,
so on a large network a door can never surface a candidate ranked 301st or
worse, however good their match; (b) the whole 300-candidate scored set is
recomputed **on every page request** — there is no stable snapshot, so a
newly-active user could shuffle which candidates fall in/out of the top 300
between page 1 and page 2 of the same door; (c) `cursor` returned is
`(v_off + v_lim)::text` when `v_total > v_off + v_lim`, else `NULL` (drops
cleanly at the end).

**Count semantics:** `like_me`/`might_know` report `v_total` (the count of
candidates that scored ≥1 within the 300-row scan — i.e. an *approximate,
scan-capped* count); `gym`/`area`/`programme`/`partners` report `v_count`,
a **separate, un-capped** `SELECT count(*)` over the same hard-filter
WHERE clause with no `LIMIT 300` — so for these four doors the door's
displayed count can be **larger** than the number of rows the scan
will ever actually be able to page through (a real inconsistency: a gym
with 500 public members would show "500" as the count but the scored list
tops out at whichever ≤300 happened to be scanned, ordered by
`last_active_at`, before offset/limit is applied — the 301st-by-recency
member is permanently unreachable via paging, no matter the offset sent).
This is a genuine mechanism defect worth flagging in the judgement, not
just a documentation nuance.

**Programme door label** re-validates via `_community_can_view_programme`
even though `tp_programme_key` is validated at *write time*
(`community_update_training_profile`, `migrate_161:1618-1631`) — a
defence-in-depth double-check the code comments call out explicitly
(security review 2026-09-06, finding 2/8).

**"People on this programme"** is a *separate* RPC/screen, not a
`find_people` mode: `community_programme_people(_id, _cursor, _limit)`
(`migrate_161:2105-2174`), reached from a programme page, gated on
`_community_can_view_programme` AND `show_programmes = true` per row.
**This one has real keyset pagination** (`(created_at, user_id)` cursor via
`_community_cursor_of`/`_community_cursor_parts`), unlike the six doors.

## C. Suggestions ("people you may know")

**Function:** `community_suggested_people(_limit int DEFAULT 20)`
(`migrate_160_community.sql:2985-3079`). Client:
`src/lib/community/feed.js:172-175` `suggestedPeople({limit=10})`, called
from `loadHub('discover', ...)` with `limit: 5` (`feed.js:110`) — the
Discover tab's "People" strip is fed by this, not by Find People.

**Candidate pool:** up to **200** active/public/non-minor/unblocked
profiles the caller does not already follow, ordered by `last_active_at
DESC` (`migrate_160:3005-3015`). No mode/key — this is one flat scan.

**Signals** (each additive, same "reasons, never percentages" rule):
1. **Shared programme** (weight 3, reason `Uses a programme you use`) — TRUE
   if: both used the same `programme_id` in `community_programme_uses`
   (co-users), OR one owns a programme the other uses (owner↔user cross,
   both directions checked via `UNION ALL`). This is a genuine "similar
   programme" signal, but it is **exact identity of the programme row**,
   never a similarity metric over programme content (no shared-exercise,
   shared-style-tag, or edit-distance comparison of two *different*
   programmes) — "similar" here means "the same catalogue entry", not
   "alike in content".
2. **Same gym** (weight 3, `Trains at <gym_label>`).
3. **Shared style** (weight 2, `Also trains <style label>`).
4. **Same area** (weight 2, `Lists <area_label>`).
5. **Same goal** (weight 1, `Same goal`).
6. **Mutual follows** (weight 2, `Followed by <n> you follow`) — YES,
   mutuals/shared follows ARE a signal here (unlike programme/gym/style/
   area/goal it is not capped in this function, unlike `find_people`'s
   `least(n,3)` cap).

**Exclusions:** `status='active'`, `visibility='public'`, `is_minor=false`,
not self, not blocked (either direction), **already-followed excluded**
(`NOT EXISTS community_follows WHERE follower=v_uid AND followee=p.user_id`)
— note this excludes only people the CALLER follows, not people who follow
the caller or people already connected; a connected-but-not-followed
person (not really possible given follow-both-ways-on-connect, SD-20) is a
non-issue in practice.

**Minimum score to appear: `v_score >= 1`** (`migrate_160:3067`) — a
candidate sharing literally nothing with the caller is never suggested, no
matter how recently active.

**Cold start:**
- **0 other users:** the candidate loop iterates zero times; `people: []`.
  Client: Discover screen simply shows nothing in that strip (no explicit
  suggestions empty-state string was found wired to this call in
  `feed.js`/`CommunityHubScreen`; it degrades silently to an absent
  section, per `loadHub`'s `Promise.allSettled` pattern, `feed.js:107-113`).
- **1 other user:** included in the 200-row scan; scored against the caller.
  If the caller shares nothing at all with that one user (no programme, no
  gym, no style, no area, no goal, no mutual follow — trivially true for a
  brand-new second user with an empty profile) the score is 0 and they are
  **excluded** — a fresh two-person network shows zero suggestions to
  either side.
  If they share even one soft fact (e.g. both left `styles` empty is not a
  match — an empty intersection never scores; but both picking the same
  `goal` on the join screen, which is a very likely coincidence given only
  four goal values, WOULD score 1) they appear.
- **5 other users:** same mechanism at 5 candidates instead of 200; nothing
  changes structurally, only the pool size.
- There is **no density/network-size floor or ceiling anywhere** in this
  function — SD-28's "no door disappears when the network is small"
  principle is upheld structurally (the function always runs the full
  scoring pass regardless of pool size), but the **practical consequence**
  of "minimum score 1" is that a near-empty network still shows nothing
  unless people happen to share a chosen fact — this is a known, accepted
  trade-off per SD-24/28's design intent, not a bug, but it does mean cold
  start genuinely surfaces very little.

## D. Training-behaviour signals — `trainingProfile.js`

**Confirmed by full read of `src/lib/community/trainingProfile.js`
(568 lines) and grep across the file and `migrate_161`:**

`loadTrainingProfile()` (lines 462-494) reads **exactly four** device
sources, matching the file's own SD-30 claim:
1. `getCompletedWorkoutStartTimestamps(uid)` — epoch-ms start times only.
2. `getWorkoutSetsSince(uid, since)` — set rows, and **only** `exerciseId`/
   `workoutId`/`createdAt` are read off each row (line 220 doc comment;
   confirmed no other field of a set row — weight, reps, RPE — is ever
   touched in `deriveTrainingProfile`).
3. `getAllExercises()` — used **solely** to build the `canonicalIds` set
   (to exclude custom/free-text exercise names from "staple lifts").
4. `getActivePlan(userId)` — for `tp_programme_key` derivation only
   (`programmeKeyFor`, lines 426-450): a Community-imported plan's source
   id, else the caller's own published programme for that plan, else a
   `style:<key>` derived from the plan's tags, else `null`.

Plus the store's own `userProfile.experience` (lazy `require`, line 485) —
**not a device read**, a Zustand store read, for the stated experience
level only.

**Bands derived** (`deriveTrainingProfile`, lines 232-320), all over a
**rolling 12-week window** (`TP_WINDOW_WEEKS = 12`):
- **`tp_days`** — a weekday counts as a "usual day" only once there are
  **≥6 sessions** in the window (`TP_DAY_MIN_SESSIONS`) AND that day
  carries **≥25%** of sessions (`TP_DAY_SHARE = 0.25`). Below 6 sessions,
  `tp_days` is `null` outright (the file's own comment: "three sessions
  would make every one of them a 'usual' day").
- **`tp_time_bands`** — up to **2** bands (`TP_MAX_TIME_BANDS`), each
  needing **≥35%** share (`TP_TIME_BAND_SHARE = 0.35`), from five fixed
  local-hour bands: morning 05-09, midday 09-14, afternoon 14-17, evening
  17-22, late 22-05.
- **`tp_sessions_band`** — average sessions/week over `min(windowWeeks,
  elapsedWeeksSinceFirstSession)`, floored at 1 week (so 2 sessions in 3
  days does not read as "6+ a week"), bucketed into `1_2`/`3`/`4_5`/`6_plus`
  with rounding boundaries at 2.5/3.5/5.5.
- **`tp_staple_lifts`** — up to **5** canonical exercise ids
  (`TP_MAX_STAPLE_LIFTS`), ranked by **distinct session count**, not set
  count (line 292: "twenty sets of one movement in a single session is not
  a staple, it is one day"). Custom exercises are categorically excluded.
- **`tp_experience_band`** — mapped from the stated `experience` string
  (`beginner|new→new`, `intermediate→intermediate`,
  `advanced|experienced|competitive→experienced`); unrecognised values
  → `null`.
- **`tp_age_band`** is the ONE exception noted in the file's own header
  (line 30-32): it is NOT derived here at all — it is server-derived from
  `user_body_profile.date_of_birth` inside
  `community_update_training_profile` (`migrate_161:1638-1665`), and the
  client sends only a boolean `share_age_band` (never a value).

**How bands are compared server-side** (all in `community_find_people`,
reproduced in full in section B): time-bands via **set intersection**
(any shared band), days via **intersection with a ≥2 threshold**,
sessions-band and experience-band via **exact equality**, staple lifts via
**set intersection with a count**, capped at 3.

**Confirmed NOT used anywhere** (grepped `split|muscle|equipment|
progression|consisten` across `trainingProfile.js` and both connections/
gym-directory migrations — the only hits are `build_muscle` as a fixed
*goal* enum value and unrelated string coincidences, `planned_muscle_
volume` in an unrelated `delete_user_data()` line, and "split a gym in
two" in a comment):
- **Split** (push/pull/legs, upper/lower, full-body, etc.) — never
  extracted or compared.
- **Exercise overlap beyond the fixed top-5 staple-lift set** — no general
  exercise-similarity or Jaccard-over-full-exercise-list signal exists;
  only the capped top-5-by-session-count list.
- **Muscle-group emphasis** — never derived or compared.
- **Equipment** (`setting` field — commercial_gym/home_gym/minimal_kit — is
  a *chosen* profile field, not a training-behaviour derivation, and it is
  **never used as a scoring or filter signal** in `community_find_people`
  or `community_suggested_people` despite being collected on
  `CommunityEditProfileScreen`. It is stored and shown on the profile card
  but appears to be write-only for discovery purposes — see divergence
  table, section H).
- **Progression** (load/volume trend over time) — never read or compared.
- **Consistency** (adherence rate, streaks, missed-session rate) — never
  read or compared; `tp_sessions_band` is an *average*, which is the
  closest analogue, but it is not a consistency/adherence metric.

## E. Location

**Area (`area_label`/`area_key`): pure free text, no gazetteer.**
`CommunityEditProfileScreen.js` line ~289: a plain `TextInput`, capped at
40 characters, run through `_community_clean_text` (blocked-terms filter)
server-side, and folded via `_community_fold` to produce `area_key`
(`migrate_162:1917-1922`, unchanged from `migrate_160/161`). There is:
- **No picker, no list, no gazetteer, no UK-places dataset** behind this
  field. A person can type literally anything ≤40 chars.
- **No coordinate** is ever attached to `area_label`/`area_key`.
- **No hierarchy.** `area_key` is a single flat fold of whatever was typed
  — "Motherwell" folds to `motherwell`; "ML1" folds to `ml1`; "Glasgow"
  folds to `glasgow`. These are three **entirely unrelated keys** with
  **zero adjacency logic** anywhere in the schema or RPCs (no
  region/nation table joins this field to anything).
- Two people who both typed "Motherwell" match on `area` mode/dimension.
  Two people who typed "Motherwell" and "ML1" (semantically the same
  place) **do not match at all** — this is a plain string-equality
  system, not a location system.

**Gym directory (`gym_venues`, migrate_162): DOES carry real location data**
— `lat`, `lng`, `postcode`, `outward`, `sector`, `town`, `town_key`,
`local_authority_code`, `local_authority_name`, `region_code`,
`region_name`, `country` are all columns on `gym_venues`
(`migrate_162_gym_directory.sql:234-260`). **But the region/nation
hierarchy is never surfaced to the client at all**: `gyms_get`'s `RETURN`
(`migrate_162:923-967`) and `normaliseVenue()`
(`src/lib/gyms/index.js:57-74`) both list every field EXCEPT
`local_authority_code/name`, `region_code/name`, and `country`. The schema
supports a region/nation hierarchy (GD-08); the app never reads it. No
screen anywhere shows "Scotland" or "North Lanarkshire" as a level a
person can browse.

**Coordinates, radius, "near me": exist in the schema and RPC layer, are
NEVER exercised by the client.**
- `gyms_near(_lat, _lng, _radius_m, _limit)` (`migrate_162:837-881`) is a
  real haversine-radius query (bounding box + `_gyms_distance_m`,
  `radius_m` clamped 1-50,000 m). GD-10's blueprint calls for mile bands
  1/2/5/10/25.
- `src/lib/gyms/index.js`'s own header comment (lines 8-18) states the
  **deviation explicitly**: *"`expo-location` is NOT in package.json...
  `near()` below is implemented against `gyms_near` for completeness... but
  nothing in `GymPicker` calls it: 'near me' today is reached only through
  the recognised-postcode chip / town search path... never through the
  device's own coordinates. No coordinate is ever requested, read, or
  stored by this module."* Confirmed by grep: `expo-location` appears
  nowhere in `src/` (only in a regression test asserting its absence,
  `src/__tests__/community.privacy.guard.test.js:310-316`) and nowhere in
  `package.json`.
- **Practical effect:** there is no "use my current location" anywhere in
  Volyume. Every gym "near" result is near a **typed postcode or town
  string**, resolved server-side to the ONSPD sector centroid — never to
  the device's GPS.

**Postcode recognition** (`src/lib/gyms/postcode.js`, fully offline, pure
regex, no ONSPD lookup client-side):
- `ML1` → `{kind: 'outward', outward: 'ML1'}` (matches `OUTWARD_RE`).
- `Motherwell` → `{kind: 'none'}` (does not match either postcode regex;
  treated as a plain town-name text search).
- Full postcode e.g. `ML1 1AA` → `{kind: 'full', normalised: 'ML1 1AA',
  outward: 'ML1'}`.

**`gyms_search` server semantics** (`migrate_162:734-826`, reproduced in
full in section F): a recognised full/outward postcode restricts to
`v.outward = v_outward` (exact district match, **no radius fallback** in
`gyms_search` itself — only `gyms_near` does radius); non-postcode text
matches folded name/town tokens with a last-token prefix fallback. A
bounding box additionally narrows results **only if the caller supplies
`lat`/`lng`** — which, per the deviation note above, the client never does.

**Region/nation adjacency: NONE.** There is no code path, anywhere in
`gyms_search`/`gyms_near`/`gyms_in_place`/`community_find_people`'s `area`
mode, that treats two different area/town keys as "nearby" to each other.
"Near me" (the `area` Find People door) is **exact `area_key` string
equality**, not radius.

**Answering the six literal test cases (as coded, against the design — not
yet reachable in production per section 0):**

| Input | Where it's typed | Exact outcome |
|---|---|---|
| **"ML1"** | `GymPicker` search bar (gym directory) | `postcode.js` recognises it as `kind:'outward'`. `gyms_search` sets `v_outward := 'ML1'`, matches `WHERE v.outward = 'ML1'` — every open/pending-visible gym venue whose outward code is exactly ML1, ranked brand/town/distance. |
| **"Motherwell"** | `GymPicker` search bar | Not postcode-shaped. Token-matched against `gym_venues.tokens` (folded name+town tokens) and `town_key`. Returns gym venues in/near Motherwell by name/town text match — not by any area/region join. |
| **"Motherwell"** | Community profile `area_label` field (Find People "Near me" door) | Free text, folds to `area_key = 'motherwell'`. Matches only OTHER profiles whose own typed `area_label` also folds to exactly `motherwell` (e.g. "MOTHERWELL", "motherwell") — no gym-directory involvement at all, entirely separate system from the row above. |
| **"Glasgow"** | Community profile `area_label` | Folds to `area_key = 'glasgow'`. **Does not match `motherwell`.** A Motherwell user searching/listing "Near me" **cannot see Glasgow users** and vice versa — confirmed: `p.area_key = v_key` is exact equality, no adjacency table, no distance. |
| **"PureGym Motherwell"** | `GymPicker` search bar | Not postcode-shaped. If a PureGym Motherwell row exists in `gym_venues` (open, or pending-and-caller-is-submitter), it is returned and client-ranked to the top via `WEIGHT.BRAND_EXACT = 1000`. |
| **"gyms near me"** | Any search field | Not a postcode, not a recognised brand/town token for most inputs (the literal phrase "near me" is just text tokens `near`,`me`). The phrase would token-match nothing meaningful; there is **no "near me" GPS button anywhere in the UI**. |

## F. Gym intelligence

**Two entirely separate gym systems coexist, one legacy, one current:**

1. **Legacy free-text `gym_label`** (migrate_160/161): a person typed any
   string as their gym; `gym_key = area_key || ':' || fold(gym_label)`
   (area-scoped, so two same-named branches in different towns are
   distinct dimensions). `community_gym_suggest` (161's original body,
   `migrate_161:2324-2396`) offered a typeahead over **labels other
   profiles in the same area had already typed** — no venue database
   involved.
2. **Current gym directory** (migrate_162, `GD-01..GD-26`): a real
   `gym_venues` table (brand, address, postcode, coordinates, status
   lifecycle, verification lifecycle) plus `gym_id`/`other_gym_ids`
   columns on `community_profiles`. **This supersedes #1 for any profile
   that uses the picker**, via a DB trigger (`_community_gym_key_sync`,
   `migrate_162:658-733`) that derives `gym_key`/`gym_label` from `gym_id`
   the instant it's set — every existing `gym_key`-keyed reader (Find
   People `gym` mode, `community_gym_summary`, the profile card) works
   unchanged. A profile that never touches the picker keeps its old
   free-text pair untouched.

**Picker mechanics (`GymPicker.js`):** 250 ms debounce, min-2-char query,
request-id guarded (same pattern as A). Calls `search()`
(`src/lib/gyms/index.js:90-99`) → `gyms_search` RPC → **server-side
dataset only** (`public.gym_venues`, joined to `public.gym_brands`) — **not**
the bundled `data/gyms/uk-gyms.v1.jsonl.gz` file, which is a **pipeline
input artefact** (per `scripts/gyms/` and the gym-database blueprint), not
something the running app reads directly; the app has no bundled-gym-data
code path at all (grep of `data/gyms` outside `scripts/gyms` and the
migration/docs turned up nothing under `src/`). **No offline gym search** —
`GymPicker` has no local fallback; offline shows the `offline` error string
(line 109-112).

Client then re-ranks the ≤40 server candidates
(`rankVenues`, `src/lib/gyms/rank.js`) — brand match (weight 1000 exact /
700 "close", Levenshtein-tolerant), then town match (300), then postcode-
outward match (500 — note: numerically this actually outranks town, despite
the doc-comment claiming "brand, then locality, then distance" ordering;
postcode(500) > town(300) is consistent with "locality" broadly but the
weights themselves are the real ranking, not a strict lexicographic
brand→town→distance order — a strong distance score plus a town match
could in principle out-rank a weak brand "close" match: 700 (close) vs
300(town)+near-max-distance(~200)=500 — brand still wins here, but this is
arithmetic, not a hard tier, worth noting for the judgement pass), then
name-token match (60 exact-prefix / 30 loose), then distance (up to 200,
only when the server returned a `distance_m`, which requires a caller-
supplied lat/lng that — per section E — never happens).

**Primary vs "other" gyms:** `community_profiles.gym_id` (primary, one) +
`other_gym_ids uuid[]` (**capped at 3**, both DB `CHECK
(array_length(...) <= 3)` and defensively in `community_set_gyms` and
client `setGyms()` `.slice(0,3)`). `CommunityEditProfileScreen.js` renders
a primary `GymPicker` plus up to `MAX_OTHER_GYMS` (3) additional pickers
(lines 337-360).

**Gym page (`CommunityDimensionScreen.js` + `community_gym_summary`,
current body `migrate_162:1569-1732`, re-issued verbatim from 161 with the
`gym:<uuid>` key resolution added): shows —**
- Member count (`v_count`), how many the reader follows among them
  (`following_count`), how many are open-to-partner (`open_to_partner_count`).
- **By-style** breakdown, top 8 style keys by count.
- **By-time-band** breakdown, fixed phrasing `"<n> usually train
  <band phrase>"`.
- Up to **20** member profile cards (`people`), ordered by `last_active_at`.
- Up to **20** member-owned visible public programmes.
- Up to **10** member-authored visible public posts, each re-checked with
  `_community_can_view_post` (not the looser person-level predicate).
- **Explicitly, by design comment (SD-31), NO "who is here now", no live
  presence, no verification badge on the summary itself.**

**"Usually trains here" inference: NONE.** `community_gym_summary`'s
member set is exactly `p.gym_key = v_key` (or the equivalent `gym_id`
join) — a **chosen fact**, never an inference from session logs, check-ins,
or location. GD-13 states this explicitly and the code matches it: *"there
is no inference from sessions, no check-ins, no live presence."*

**"People at this gym" privacy:** listed people are exactly those with
`status='active' AND visibility='public' AND is_minor=false AND
gym_key=v_key AND NOT blocked-by-viewer` — i.e. **opt-in by virtue of
having set a public profile with that gym**, not a separate per-gym
opt-in toggle. A followers-only profile at that gym is invisible to the
gym page even though they "chose" the gym.

**Nearby-gyms capability:** `gyms_near` exists (haversine + bounding box,
metric radius clamped 1-50,000 m) but, per section E, is **never invoked
by the client** — no coordinate is ever supplied. There is no "nearby
gyms" list anywhere reachable in the shipped UI.

**Confirm / report / closure / rename flows:**
- **Confirm** (`gyms_confirm_submission`, `migrate_162:1236-1295`): a
  **second, distinct** account (not the submitter) confirms a `pending`
  venue → `gym_venues.status` flips to `open`,
  `verification_status = 'user_submitted_verified'`. Rate: 20/hour
  (`_community_rate_check(..., 'gyms_confirm', 20, 20, interval '1 hour')`).
  UI entry point: `CommunityDimensionScreen.js` "Is this gym real? Confirm
  it" button, shown only when `isPendingVenue(venue)` is true.
- **Report** (`gyms_report`, `migrate_162:1308-1358`): six fixed kinds —
  `closed`, `wrong_name`, `wrong_location`, `duplicate_of`, `not_a_gym`,
  `other` (`REPORT_KINDS`, `src/lib/gyms/index.js:36-43`). **Two distinct
  reporters of the same kind** set `gym_venues.needs_review = true`
  (GD-12). Rate: 10/24h.
- **Closure/rename:** no dedicated "close this gym" or "rename" user flow
  exists — closure happens only via a **moderator** action
  (`gyms_review_submission` with `_action='reject'` → `status='closed'`)
  or a report escalating to moderator review; there is no self-service
  rename RPC at all (a submitter cannot edit their own pending venue's
  name after submission — only confirm/report exist as post-submission
  actions).
- **Moderator RPCs:** `gyms_review_submission` (approve/reject/merge, with
  merge cascading `community_profiles.gym_id`/`other_gym_ids` to the
  surviving venue and de-duplicating) and `gyms_review_report`
  (resolve/dismiss, recomputing `needs_review` across **all** open kinds,
  not just the dismissed one — review-35 finding 12 fix). **No moderator
  UI screen exists in the client** (`gyms_review_submission`/
  `gyms_review_report` are not imported by any screen; the migration
  header itself notes `not_allowed`/`already_confirmed` "fall back to the
  client's generic `unavailable` toast today" because "there is no
  consuming screen for confirm/moderate yet" — this refers to the
  moderator side specifically).

**"Add gym" (`gyms_submit`, `migrate_162:990-1210`), exact flow:**
1. Field validation: name ≤60 chars, address ≤200, town ≤80 (all run
   through `_community_clean_text` blocked-terms gate), website must match
   `^https?://` and ≤200 chars, operator ≤80 chars, postcode must be a
   **full, valid UK postcode** (`_gyms_postcode_full_valid`) — an outward-
   only postcode is rejected at submission (`invalid_postcode`) even
   though it's accepted for search.
2. Rate: **3 submissions per 24 hours** per user.
3. Coordinates: resolved from `gym_postcode_sectors` (ONSPD sector
   centroid) — if the sector isn't seeded, `invalid_postcode` even though
   the postcode shape is valid.
4. **Duplicate detection, exact fields and threshold** (review-35 finding
   9 fix, since sector-centroid coordinates make a distance test
   meaningless): text-only, on **token Jaccard similarity**
   (`_gyms_token_jaccard`, over `_gyms_tokens_of(name, town)` — folded
   space-split tokens of name+town combined):
   - Same **postcode unit** (`gym_venues.postcode` compact-equal) AND
     Jaccard ≥ **0.6** → treated as a duplicate.
   - OR same **outward code** alone AND Jaccard ≥ **0.85** (looser area
     match, needs near-identical name) → duplicate.
   - Scoped first to the submission's own outward code
     (`gym_venues_outward_idx`), so this is not a full-table scan.
   - Only venues the **caller can see** (`_gyms_visible`) are offered back
     as a duplicate (privacy: a stranger's invisible pending submission is
     never named to this caller as "did you mean X").
5. **What the user sees on a duplicate hit:** `{duplicate_of, display_name}`
   → `CommunityGymAddScreen` shows *"Did you mean `<display_name>`?"* with
   a "Use this gym" button that selects the existing venue instead of
   creating a new row.
6. **"Twin" handling (review-35 finding 22):** if the *same* text-Jaccard
   match hits a **`pending`** venue the caller cannot see (someone else's
   independent pending submission of the same real gym), rather than
   silently creating a **second** pending row for the same place, this
   caller is recorded as a **distinct confirmer** on the existing venue —
   which can itself flip that venue to `open` if this is the second
   distinct confirmer. The caller only ever sees the venue's own
   id/display_name/status back, never who else submitted it.
7. **On success (no duplicate/twin):** a new `gym_venues` row is inserted
   with `status='pending'`, `verification_status=
   'user_submitted_pending'`; a `gym_submissions` row (sharing the same
   `id`); a `gym_venue_sources` provenance row (`source='user'`); TWO
   `gym_venue_history` rows — a `'submit'` entry and an **implicit
   'confirm' entry by the submitter themselves** (so the submitter counts
   as confirmer #1, and only ONE more distinct confirmer, not two, is
   needed to reach the "2 distinct confirmers" open threshold).
8. **Pending-state UX:** `isPendingVenue()`
   (`src/lib/gyms/index.js:275-277`) checks
   `verification_status.startsWith('user_submitted_pending')`.
   `GymPicker`'s `GymRow` shows a "Pending" badge on such rows (per the
   file's own header comment); the submitter can select it immediately
   ("immediately selectable by its submitter" — `_gyms_selectable`/
   `_gyms_visible` both special-case the submitter's own pending
   submission as visible/selectable to them only); it becomes selectable
   by *everyone* once `status` flips to `open` (second distinct confirmer,
   or moderator approval).

## G. Age band — CONFIRMED INERT (product review 73 finding 6 is correct)

  (`'tp_age_band', CASE WHEN v_viewable THEN p.tp_age_band END` —
  `migrate_161:847`/`migrate_162:2093`), i.e. visible to a follower/self
  viewing that ONE profile.
- **Used as a filter or scoring term: NOWHERE.** Exhaustive check of every
  scoring block in `community_find_people` (both the 161 and superseding
  162 bodies, reproduced in full in section B) and
  `community_suggested_people` (section C): `tp_age_band` never appears in
  either function's `IF`/scoring logic. It is also absent from
  `community_dimensions_me`/`community_dimension` (no `age` dimension kind
  exists — the closed set is `('style','programme','gym','area')`,
  `migrate_160:3266`).
- **Conclusion: CONFIRMED, not merely plausible.** The age band is
  computed, stored, validated, and displayed on an individual profile
  card, and does **nothing else** — no age-band door, no age filter, no
  age-based ranking signal, no age dimension page. It is read-only

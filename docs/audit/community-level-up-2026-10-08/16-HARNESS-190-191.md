# Harness proof: migrations 190 and 191 on PostgreSQL 16 (2026-10-08, lane 3S)

Scope: every acceptance fixture of migrate_190 (feed scopes) and migrate_191 (presence, group chat, decline, challenges, recipients RPC), run as real SQL, as the `authenticated` role, inside one transaction that is rolled back. Nothing was applied to any real project.

## How the harness was built

- Docker: the CLI exists but there is no daemon here (`failed to connect to the docker API at unix:///var/run/docker.sock; check if the path is correct and if the daemon is running: dial unix /var/run/docker.sock: connect: no such file or directory`). So `docker run postgres:16` was not possible.
- Instead: the PostgreSQL 16.15 server installed in the container (`/usr/lib/postgresql/16`), a throwaway cluster started as the `postgres` user, unix socket only. Scripts and results are in the session scratchpad (`base.sql`, `run.sh`, `fixtures.sql`). The data directory is `/tmp/pgharness`, NOT under the scratchpad, because the scratchpad's parent (`/tmp/claude-0`) is mode 700 and the postgres user cannot traverse it. Nothing is under the repo.
- Base (README recipe: stubs for what the Community chain needs): roles `anon`, `authenticated`, `service_role`; `auth.users`; `auth.uid()` reading `request.jwt.claims`; Supabase-style default grants to the three roles; stubs for `user_body_profile(user_id, date_of_birth)`, `partnerships`, `user_prefs`, `programmes`, `workout_sets`, `users_profile`. The real migrate_017, 019 and 044 supply `ed_pattern_flags`, `consent_log` and `notification_preferences`.
- Chain applied in order, each file in its own transaction with `ON_ERROR_STOP`: 017, 019, 044, then 160 to 189 (all of them, including 176, 177, 178, 180, 182, 183 to 187), then 190, then 191. Every file applied clean, including each file's own acceptance DO block (190 has none executable; 191's executable catalogue block passed).
- Re-run: 191 applied twice more and 190 once more over the finished chain, no error (idempotent).
- Findings about the harness, not the migrations: an adult needs a `user_body_profile.date_of_birth` row (migrate_174 reads an unknown date of birth as a minor, so `community_set_show_training_now` correctly refused users with none); fixture time is one transaction so `now()` is constant, hence group `joined_at` was backdated a day for the unread count.
- 191 file md5 at the time of the run: `d6c8d0f633632b52edeb15649d8ec1dd`.

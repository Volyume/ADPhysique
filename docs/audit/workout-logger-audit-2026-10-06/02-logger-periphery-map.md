## 1. Entry paths

The logging screen is `ActiveWorkout`, registered ONLY in the Today stack (`HomeStack`): src/navigation/RootNavigator.js:476 (`headerShown: false`, `heroZoomTransition`). Every other tab reaches it through the parent-tab form `navigate('HomeTab', { screen: 'ActiveWorkout', initial: false })` (or `navigateCrossTab`, src/navigation/navigateCrossTab.js). There is no route that resumes a session by itself: a session is created by `createWorkout` (a database row with `is_completed = 0`, src/lib/database.js:3927) and made live by the store's `startWorkout` (src/store/useAppStore.js:1758), then the screen is navigated to. Every start site below calls both, in that order.

Common to every start site that hydrates a routine: the logger is handed `initialExercises` shaped `{ exercise, routineExercise, sets: [], supersetGroupId, groupKind, roundRestSeconds }` (src/screens/HomeScreen.js:1730-1739, repeated at PlansScreen.js:857 and :1139, PlanDetailScreen.js:352, RoutineDetailScreen.js:1125 (built from the swap-applied rows), WorkoutHistoryScreen.js:328), read by `getRoutineExercisesWithDetails` (src/lib/database.js:5049). `startWorkout` overwrites any live session unconditionally: no start site checks `activeWorkout` first (src/store/useAppStore.js:1758-1775; the only guard is Home's single-flight ref, HomeScreen.js:1725). Observed: the replaced session's `workouts` row and its sets stay in SQLite as an incomplete row that no screen lists (section 12 item 8).

## 2. Exit paths

The only code that leaves ActiveWorkout is in src/screens/ActiveWorkoutScreen.js (A1 owns the screen; the seams are named here).

1. **Header close "Cancel workout"** (src/components/workout/WorkoutHeader.js:59-69, testID `volyume-workout-close`) -> `handleCancelWorkout` (ActiveWorkoutScreen.js:1980).
   - No logged sets and nothing typed or in progress: `endWorkout()`, dismiss the (disabled) notification, `navigation.goBack()`, silently (:1986-1993).
   - Otherwise the Discard modal (:6394-6420): "Keep training" closes it; "Discard workout" -> `discardWorkout('ActiveWorkoutScreen.discardModal')` (:1946). Discard hard-deletes the incomplete workout and its sets in one transaction (`deleteIncompleteWorkout`, src/lib/database.js:4067-4098, also tombstones its `session_constraint_effects` row), bounded to 8 s (:1957-1960), stops a running rest timer (:1971), `endWorkout()`, `goBack()`. A thrown delete or the 8 s bound keeps the person on the screen with the toast "Couldn't discard this workout, try again" (:1972-1975). Modal copy: "This will delete the current workout session. Your plan will not advance." (:6399-6401).
2. **Android hardware back**: a `BackHandler` listener calls the same `handleCancelWorkout` and always returns true (:2001-2008). Observed: there is no "leave but keep the session" back action on Android; back is cancel/discard.
3. **iOS edge-swipe back**: not overridden. Observed: the stack library sets `gestureEnabled = Platform.OS === 'ios' && animationEnabled` (node_modules/@react-navigation/stack/lib/commonjs/views/Stack/CardStack.js:129); the only app-side override is `animationEnabled: false` under Reduce Motion (RootNavigator.js:394); no `gestureEnabled` appears anywhere in src/. Suggests: on iOS a swipe pops to Today with the session still live (the Continue card and mini bar then show), unlike Android back (not run on a device; section 12 item 9).
4. **Header "Finish workout"** (WorkoutHeader.js:99-108, testID `volyume-workout-finish`; hidden via `showFinish` when the bottom bar itself offers Finish, WorkoutHeader.js:44-48) -> `handleFinishWorkout` (ActiveWorkoutScreen.js:3787), double-tap guarded by `finishingRef` (:3789-3790). The route through the confirms:
   - Nothing at risk (`shouldConfirmBeforeFinish` false and nothing typed): finish immediately (:4142-4145).
   - Ended early (some planned exercise has sets, another has none, a programme week and routine id are known): the alert from `endEarlyConfirmation` (src/lib/blockProgression.js), confirm runs `runFinish({ resolution: 'ended_early', ... })` which closes the workout and writes the ENDED_EARLY resolution in one transaction (`finishWorkoutWithSessionResolution`, database.js:6627; alert at ActiveWorkoutScreen.js:4174-4208).
   - Nothing saved (database read succeeded and 0 sets): "Nothing logged yet" with "Keep going" / "Discard workout" (:4224-4245).
   - Otherwise "Finish workout?" with the saved set and exercise count from `buildSessionReport` (:4247-4262).
5. **`runFinish` / `doFinish`** (:4011, :3803): appends the session's constraint effects (`appendSessionConstraintEffects`, :4011-4110), reads DB sets and the shared lookup, builds ONE report (`buildSessionReport`, src/lib/sessionReport.js:158), then `updateWorkout(id, { endedAt, durationMinutes, isCompleted: true, name, setCount: workingSetCount, totalVolume: tonnage })` (`workoutUpdate` :3858-3865, written :3866-3875). Fire-and-forget after that: clear a pending re-entry ease, `publishConsistency`, `workout_completed` and `first_workout_logged` telemetry, `writeWidgetSnapshot`, `scheduleActivationNudge`, `refreshHabitDerivedTrainingSchedule`, `relayWeighInAfterTrainingReturn`, `syncWorkout` (:3888-3963). Then `endWorkout()` (clears the snapshot), completion haptic, and `navigation.replace('WorkoutSummary', {...})` (:3979). A failure shows "Couldn't finish workout" and re-arms the guard (:4113-4127).
   - Params passed to WorkoutSummary (:3979-4005): `workoutId, sessionAdjustments, routineId, startedAt, endedAt, durationMinutes, exerciseCount, setCount, workingSetCount, tonnage, exerciseNames, detectedPRs, exerciseData` (one entry per exercise with a logged set, in first-logged order, each with `loggedSets`). Observed: `endedAt` in the params is a second `Date.now()` (:3984), not the value written to the row (:3859).
6. **Stale-session modal** "Resume workout?" with Resume / Finish workout / Discard (:5565-5602), opened on mount when `lastActivityAt` is more than 4 h old (:2032-2037). Suggests: `restoreActiveWorkout` sets `lastActivityAt: Date.now()` on restore (useAppStore.js:1854), so after a kill-and-restore the modal cannot fire; it can only fire in a process kept alive more than 4 h (not run; section 12 item 2).
7. **Leaving without ending**: backgrounding or killing the app keeps the session (snapshot `@volyume_active_workout` written by `_persistActiveWorkout`, useAppStore.js:193-230). Switching tabs is impossible from the logger (tab bar hidden), so the in-app leave-and-return pair is: iOS swipe back (item 3) and then the mini bar or Continue card. No start handler reads `activeWorkout`; only Home swaps its hero for the Continue card (section 12 item 8).

Where each exit lands:
- Cancel, discard, nothing-logged discard, stale discard: `navigation.goBack()` pops the Today stack to its previous route, which is Today (`Home`) for every start site (BuildWorkout used `replace`; the others push over Home with `initial: false`, RootNavigator.js:1163-1171 rationale). Observed: no start site records which tab it came from and the tab navigator has no `backBehavior` setting (grep of RootNavigator.js), so a session started from Train, Progress or Plans returns to Today, not to the originating tab.
- Finish: `replace('WorkoutSummary')` (the logger leaves the back stack), so the first thing behind the summary is Today. Summary "Done" then `popToTop()` to Today (section 4).
- Exits that touch the store: `endWorkout()` (useAppStore.js:1907-1940) clears the session slice, retires the end-of-rest alert (`cancelRestEndNotification`) and rewrites the snapshot as empty; the iOS Live Activity and Android rest service are stopped by `stopRestTimer` (discard path :1971) or by the 'active' sweep on the next launch (`restoreActiveWorkout` calls `endAllActivities`, useAppStore.js:1795-1799).

## 3. The session and set data model

Everything below is the on-device SQLite (SQLCipher) schema in `src/lib/database.js`, the source of truth on the phone. Observed: base tables are created by one `CREATE TABLE IF NOT EXISTS` block (database.js:250-343), then evolved by `SCHEMA_MIGRATIONS`, an array of 92 versioned, additive entries run one transaction per version (array starts database.js:492; `CURRENT_SCHEMA_VERSION = SCHEMA_MIGRATIONS.length` = 92, :2926; runner :3231-3300). Version numbers below are array index + 1. There is NO table of personal records: records are derived at read time from `workout_sets` (src/lib/__tests__/campaign10m.estMaxRecordConsistency.test.js:48-56 pins "the local schema never creates a personal_records table"; database.js:10007-10010 and :10124-10125 say so in comments on the recap reads).

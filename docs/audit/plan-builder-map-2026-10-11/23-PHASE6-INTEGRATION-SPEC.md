## Lead rulings (D33)

**R60 Plan facts.** An engine-built plan's `plan_facts` keeps the version 2 shape every current reader uses (top-level `version: 2`, `slots`, `thin`, `roles`, `weeklyTargets`, `exposureShares`, `sessionCaps`, `lightCaps`, `gapRanks`, `rirLadder`, `sessionMinutesAtPeak`, `overTime`, `overCeilings`, `notes`, `limitedBy`, `recoverySafeMax`, `builtFactor`, `readiness`, `family`) and adds `structure`:
```
structure: {
  version: 3,
  category, days, lengthMinutes, equipment, experience, focus: [engine keys],
  sessions: [{ routineId, key, name, exercises: [{ routineExerciseId, exerciseId, name, muscle /* engine key */, pattern, kind, peak, weeks: [{ sets, rir }], restSec, repRange, nextDayException }] }],
  checks: { ok, faults: [] /* checkPlan */, sense: [] /* senseCheck codes */ },
  report: { minutes, longestMinutes, needsLengthChoice, suggestedLength, daysThatFit, focusResults, focusUntrainable, untrainableSets, belowMinimum, belowTypical, fewerSetsThan, focusDropped },
}
```
Why not a top-level version 3: about 20 readers test `facts.version === 2` (sessionAdjustments, coachApply, checkinPlan, effectiveLandmarks, database recordTypedSetCount and two more, swapCarry, planRebuild, PlanDetailScreen, ProSetupCompleteScreen, ActiveWorkoutScreen, RoutineDetailScreen). Bumping it would silently switch off serving, swaps, typed sets, check-ins and the explanation for every new plan. `structure.version === 3` marks an engine plan; phase 7 teaches each post-build path to read `structure` and re-run the checks.

**R61 Muscle keys.** The compat fields use today's keys. The map: lats, upper_back -> back; glute_max, glute_med -> glutes; every other engine key maps to itself where it exists in `VOLUME_LANDMARKS` (algorithms.js) and is otherwise left out of the compat fields (it stays in `structure`). `weeklyTargets[oldKey][w]` = the sum of the week's sets of the exercises whose engine muscle maps to it (own sets, as v2 stores them; verify v2's meaning from `plannerV2PlanFacts` and match it). `slots[routineId][exerciseId] = { muscle: oldKey, kind, credits }` in the v2 meaning (derive kind and credits the way v2 does from the exercise row / PATTERNS credits mapped to old keys).

**R62 Weekly serving.** When `facts.structure?.version === 3`, the sets served for an exercise in block week w are `weeks[w-1].sets` of the matching structure exercise (matched by routineExerciseId, else by exerciseId within the routine), and the RIR is `weeks[w-1].rir` where it is higher than the block's week RIR (the next-day exception). Typed set counts (`facts.typed`) still win, as today. A routine exercise with no structure match (added by hand later) is served as today. prescribeWeek is not used for structure exercises. `planned_muscle_volume` rows are written from the compat `weeklyTargets` (source 'template'), so Progress and the heatmap keep their planned bands.

**R63 Routes.** With the switch on and no style pool: `generateAndSavePlan`, `generatePlanDryRun`, `assessScheduleFit` and `planGeneratedRebuildV2` build through `buildStructurePlan`. Style-pool plans (kettlebell, circuit tags) keep today's generator. There is NO fallback to the old planner when the engine refuses or asks: a refusal or a question is returned to the caller (R65). An engine exception is logged (`logError('structure.build', e, {...})`) and returned as a calm failure, never a silent old-style plan.

**R64 Inputs.** goal: the profile's trainingGoal after `migrateProfileGoals` (the engine's `rulebookCategory` aliases the rest). experience: `competitive` -> `advanced`. equipment: as stored (kettlebells and bands never reach generation). lengthMinutes: the profile's session length. focus: `profile.planWeakPoints` labels mapped: Chest, Upper Chest -> chest; Lats / Back Width -> lats; Back Thickness -> upper_back; Side Delts -> side_delts; Rear Delts -> rear_delts; Front Delts -> front_delts; Biceps -> biceps; Triceps -> triceps; Quads -> quads; Hamstrings -> hamstrings; Glutes -> glute_max; Adductors -> adductors; Calves -> calves; Core / Abs -> abs; Traps -> traps; de-duplicated in pick order, at most three (the pickers already cap at three; the engine reports any extra). library: the same filtered generation library the V2 path uses (`generationLibrary`, exclusions and capability applied); `loggedExerciseNames` from `plannerV2LoggedNames`. Every engine exercise must carry a real `exerciseId`; an exercise whose id is a name (no library row) fails the build with a logged error rather than saving a broken row.

**R65 The person's choices.** The engine's questions reach the person in the existing places:
- `generatePlanDryRun` returns `{ ok: true, plan, structure: { needsLengthChoice, suggestedLength, daysThatFit, focusQuestions, messages } }` or `{ ok: false, refusal: { reason, suggestedDays, suggestedLength, minimumDays, text } }`.
- PlanPreviewSheet shows the real length (`report.minutes` peak, not the input minutes), the engine's message lines, and any refusal text, beside today's `fit` block, using the same components and styles (no new visual elements).
- Onboarding (no preview) uses `assessScheduleFit`: with the switch on it returns the engine's refusal or length question in the shape its fit review already renders (`fitReview`), so the person picks before the plan is saved.
- All words come from one pure module, `src/lib/structure/messages.js`: the renderer's message functions (`docs/audit/plan-builder-map-2026-10-11/tools/render-structure-plans.jest.js`) moved there verbatim and exported; the renderer then imports them, so the page the founder signs off and the app say the same words. The audit-only parts (the weekly-sets footer, raw keys) stay in the renderer.

**R66 Saving.** One transaction, as saveWithPlannerV2: createProgramme, createRoutine per engine session in the engine's order (after `startIndex`), addExerciseToRoutine per exercise with sets = week 1 sets (`weeks[0].sets`), repMin/repMax from `repRange`, restSec, selection reason null unless an existing SELECTION_REASON code fits, then `setProgrammePlanFacts` with R60's facts (routine and routine-exercise ids filled in after the inserts). Then activation (keep block or new block) and the weekly rows as today.

**R67 Founder's plan.** Programme `31a3b33c-5548-4c54-9b9a-dd3a927b2c49` is never deleted, regenerated or rebuilt by any path (founder standing order). Phase 6 adds the guard constant `PROTECTED_PROGRAMME_IDS` in `src/lib/structure/release.js` and checks it in planRebuild's run in planRebuild's run. Archiving is not deleting: when the person saves a new plan themselves from a screen, the old plan is archived as today (their own choice; skipping it would leave two active plans). Amended 2026-10-12 after the phase 6 review.

**R68 Tests.** With the switch mocked on (`jest.mock('../structure/release', ...)`): the facts written for a sample plan (structure block present, compat fields in old keys, sums match), serving returns the engine ladder for weeks 1 to 6 including the deload and the next-day exception RIR, a refusal returns no saved plan and no old-planner fallback, the focus label map, competitive -> advanced, the protected programme is skipped by rebuild. With the switch off: the existing suites unchanged.

## 0. Legend

Resolution (how a surface turns a set's `exercise_id` into an exercise):
- LIB-F: `getAllExercises()` map. It FILTERS `deleted_at IS NULL` (`src/lib/database.js:3365`) and is cached.
- LIB-U: an unfiltered read of the `exercises` table (`getAllExercisesIncludingDeleted` `database.js:3379`, `SELECT * FROM exercises` `database.js:6083`, `SELECT id, primary_muscle, secondary_muscles FROM exercises` `database.js:4093`).
- LIB-S: `getExerciseById` (`database.js:3383`): unfiltered and survivor-aware since D217.
- JOIN-I: SQL INNER JOIN on `exercises` (an unknown id drops the row; no `deleted_at` predicate, so a soft-deleted row still joins).
- JOIN-L: SQL LEFT JOIN on `exercises` (an unknown id keeps the row with a null name and a defaulted type).
- SNAP: reads the set's own `exercise_name` snapshot.
- NONE: no per-exercise resolution (pure totals).

The five cases asked for: (a) id unknown locally (never seeded, other device, retired id before D217); (b) soft-deleted custom exercise (`deleted_at` set, EL-18); (c) live custom exercise (`is_custom = 1`, random `uid()` id); (d) set has only a name snapshot (an unresolved id with `exercise_name` present); (e) `primary_muscle` null or outside the 17 listed muscles (the corpus has exactly the 17 on all 918 live exercises; only a custom exercise created with no muscle, a foreign client row or a legacy `shoulders` row can be outside).

Case outcomes: OK = counted and shown correctly; TOT = counted in totals but dropped from the breakdown; DROP = silently dropped everywhere on that surface; MIS = mis-credited or mis-named (said which).

Row-rule shorthand: `wu-` warm-up excluded; `ex-` explosive (`evidence_class` contains `ballistic`) excluded, `ex+` included; `null+` a `set_type` NULL row is counted, `null-` it is excluded (`set_type != 'warmup'` is false for NULL in SQL); `w0-` needs weight > 0 (a bodyweight set at 0 is dropped), `w0+` counted; `r0-` needs reps > 0; `sem` load semantics applied (per_hand x2, assisted x0), `sem-` not applied; `type-` distance/duration excluded from load, `type+` included; `cl-` myo-reps/rest-pause excluded from e1RM, `cl+` included. AMRAP, dropset and `failed` rows get no special rule on any surface (no reader tests `is_amrap` or `failed`), so they count as working sets everywhere.

Completed rows: `C` = joined to `workouts.is_completed = 1`; `id` = read by workout id (the caller passes a completed workout); `any` = no completion test.

## 2. Findings

Order: the ones a person meets first (a set or an exercise missing, a wrong name, two numbers for one thing), then eligibility and basis defects, then smaller items. Severity words: DROPS DATA, MIS-CREDITS, MIS-NAMES, INCONSISTENT COUNTS, OK.

Findings that share one fix, so one landing can take them together: lookup (F-1 to F-6: one unfiltered, survivor-aware exercise lookup with a snapshot-name fallback); working-set rule (F-17 to F-21: one shared predicate and one session predicate); tonnage basis (F-8, F-9: tonnage and e1RM reduced in JS with the type map and load semantics); e1RM eligibility, evidence class on the row and the deload rep average (F-10 to F-16, F-25); write side and display (F-7, F-22 to F-24).

### F-1. The history view of a workout drops every exercise the filtered library cannot resolve
- Where: `src/screens/WorkoutSummaryScreen.js:786` (`getAllExercises()`), `:912`, `:919-920`; library read `src/lib/database.js:3365`.
- Deciding lines: `const exerciseMap = Object.fromEntries(allExercises.map(e => [e.id, e]));` then `if (!ex) continue;`, where `getAllExercises` is `SELECT * FROM exercises WHERE deleted_at IS NULL ORDER BY name ASC`.
- Consequence: open an old session from History. Exercises, Working sets and Total lifted still count the exercise (they arrive from History's own rows, `WorkoutHistoryScreen.js:86-101`), but the list under them does not show it. The share image's Top lift options and top set are built from the same list (`:1150-1186`), so the exercise cannot be chosen there either. This is the D217 symptom for every cause of "unresolved", not only a retired id: an id never seeded (another device's custom exercise before its pull), a soft-deleted custom exercise (EL-18), or a set known only by its name snapshot. A warm-up-only exercise in this list renders " x -" (`:1760`, `recommendedSets` is undefined on history rows).
- Severity: DROPS DATA.
- Smallest fix: build each group's name from the unfiltered, survivor-aware lookup (the `getExerciseById` rule), then the set's own `exerciseName`, then "Exercise"; never `continue`. Keep the exercise in the list even when it has no muscle.

### F-2. History, Progress "Recent sessions" and "Rate your last session" name exercises through the filtered map and print nothing, or "Unknown", on a miss
- Where: `WorkoutHistoryScreen.js:91-94`, `:480`, `:634`, `:367`; `AnalyticsScreen.js:581-583`; `ReadinessCards.js:263`; `HomeScreen.js:1864`.
- Deciding lines: `const allExerciseNames = exerciseIds.map(id => exerciseMap[id]?.name).filter(Boolean);`, `{exerciseNames.join(', ') || 'No exercises logged'}`, `name: exerciseMap[s.exerciseId]?.name || 'Unknown'`.
- Consequence: a session whose exercises do not resolve reads "27 sets" beside "No exercises logged" on the collapsed card and "Unknown" on the expanded row. Search by exercise name and the Upper / Lower / Full body chips (`primaryMuscles` from the same map, `:94`) cannot find it. "Repeat as-is" with no routine silently leaves the exercise out (`:367` `if (!exercise) return null;`), while Home's repeat of the same kind of session keeps a soft-deleted one (`HomeScreen.js:1864` uses `getExerciseById`). The Progress root slices four ids before dropping unresolved ones (`AnalyticsScreen.js:581`), so it can list fewer names than History for one workout. Three hand-copied builders (History `:63-102`, Analytics `:577-596`, ReadinessCards `:257-275`) can drift.
- Severity: MIS-NAMES (DROPS DATA in search, filter and repeat).
- Smallest fix: one shared session-row builder used by all three, resolving names by the F-1 rule; History's name line is then never empty when sets exist.

### F-3. Per-muscle credit runs on two different libraries, so one deleted custom exercise is counted in some places and dropped in others
- Where, drops (LIB-F): `WorkoutSummaryScreen.js:786-793`; `VolumeHeatmapScreen.js:404-412` -> `volumeLogged.js:65-75`; `HomeScreen.js:1320-1325`; `useProgressData.js:175`, `:339`, `:360`; `CoachReviewScreen.js:239`. - Deciding lines: `if (!exercise) continue;` (`algorithms.js:282`) over a map built from `getAllExercises()`, against `SELECT id, primary_muscle, secondary_muscles FROM exercises` (`database.js:4093`, no `deleted_at` predicate).
- Consequence: sets on a soft-deleted custom exercise are credited by the heatmap's trend chart, the check-in's week-over-week volume (a coach input), in-session adjustments, Recovery and the block ledger, and dropped by the heatmap rows, "N sets logged", per-week `loggedSets` (`VolumeHeatmapScreen.js:365`), the Progress strip, the summary volume card, the Home and Consistency block rows and the coach review. - Smallest fix: one `getExerciseLookup()` (unfiltered, survivor-aware) for every credit, recency and breakdown reader; keep `getAllExercises()` for pickers and plan generation.

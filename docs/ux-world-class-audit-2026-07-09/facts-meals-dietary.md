## Facts

**1. Meal data model** — `src/lib/food/` (46 modules + `sources/`, `normalisers/`, `__tests__/`). Bundled meal library is `curatedMeals.js`: 40 hand-authored meals (`CURATED_MEALS`), schema `{ id, name, diet, slots[], components:[{food,g}] }`. `diet` is one of `DIETS = ['omnivore','vegetarian','vegan']` (broadest-qualifying tag; cascade `vegan ⊂ vegetarian ⊂ omnivore` via `dietAllows()`). `slots` ∈ breakfast/lunch/dinner/snack/preworkout/postworkout/any. Macros are never hand-typed — computed from `curatedFoods.js`, a per-100g staple table (~90 foods, UK CoFID values).

Dietary/allergen tagging **already exists**: `foodRoles.js` carries a `TAGS` map of FSA's 14-allergen vocabulary (`cereals_gluten, milk, eggs, fish, crustaceans, soya, nuts, peanuts, sesame`, others unused) keyed per curated food, exposed via `tagsOf(foodKey)`. Grep hits for vegan/vegetarian/halal/allerg/gluten/dairy/nut etc. found 41 files; **no halal/kosher/pescatarian anywhere** — only vegan/vegetarian/omnivore + FSA allergens.

**2. Suggestion engine** — Two layers, both pure/deterministic (no LLM, no randomness):
- `mealSuggest.js`: `rankSuggestions({targets, consumed, savedMeals, foods, slot, mealsLeft, limit})` → `remainingMacros()` → `perMealMacros()` → `fitScore()` (protein-first, calorie-overshoot penalty, fat-alignment nudge) via `suggestFood`/`suggestMeal`, filtered by `slotMatches()`. This is the diary "what should I eat" ranker; it does **not** itself filter by diet/allergen — callers must pre-filter candidates.
- `mealPlanAssembler.js` + `mealPlanService.js`: builds full day/week plans against calorie/macro targets with a greedy/precision solver, respecting safety floors (`floorApplied`, `withinTolerance:false` reported rather than under-feeding).
- **Diet + allergen filtering already exists** at the plan layer: `planPreferences.js` — `mealAllowed(meal, prefs)` checks diet axis, a protein-anchor-quality policy (omnivore plans must anchor on real animal protein; no legume/soy anchors), then every component via `foodAllowed(foodKey, prefs)` which checks `excludeFoodKeys` and `excludeTags` (FSA tags) — i.e., a working exclusion/allergen mechanism already ships for the curated library and plan assembler, tested in `planPreferences.test.js`, `mealPlanAssembler.test.js`, `foodRoles.test.js`, `mealSwap.test.js`. `mealSuggest.js`'s diary-suggestion ranker is the one path NOT yet wired to these prefs (per file header, screen layer "gathers and normalises candidates" — worth checking whether `FoodSearchScreen`/diary suggestion call sites apply `foodAllowed` before calling `rankSuggestions`).

**3. Food search sources** — Waterfall (`waterfall.js`) across `sources/localCache.js` → bundled `curatedFoods`/seed → `sources/liveOff.js` (OpenFoodFacts live API) → `sources/usda.js` (USDA FoodData Central, needs `EXPO_PUBLIC_USDA_API_KEY`). OFF `_toRow()` ingests only: `food_ref, source, name, brand, serving_g, serving_label, kcal_100g, protein_100g, carbs_100g, fat_100g, fibre_100g, barcode_ean` — **OFF's `allergens_tags` / `ingredients_analysis_tags` / `traces_tags` fields are never requested or ingested** (the `fields=` query param omits them entirely); same for USDA (`normaliseUsdaFood`, not read but by symmetry of fields fetched, no allergen data in FDC branded response used here). Local `foods` table schema (`database.js` line 866): `id, source, source_id, barcode_ean, name, brand, serving_g, serving_label, kcal_100g, protein_100g, carbs_100g, fat_100g, fibre_100g, sodium_100g, sugar_100g, <micronutrient columns>, verified, fetched_at, created_at, updated_at` — no allergen/ingredient/tag column. `custom_foods` table has the same macro shape, no allergen field either.

**4. Profile/settings** — Diet preference lives on `userProfile` (Zustand store) as `dietPreference` (default `'omnivore'`), editable in `SettingsProfileScreen.js` (chips: Omnivore/Vegetarian/Vegan, copy: "Filters the meals Volyume suggests."). Plan-specific prefs also on `userProfile`: `mealPlanExcludeFoods`, `mealPlanExcludeTags`, `mealPlanMealsPerDay`, `mealPlanVariety`, `mealPlanFatConvention`, `mealPlanPeriWorkout`, `mealPlanPinnedMeals` (`useAppStore.js` ~lines 1685-1720). `mealPlanService.js:preferencesFromProfile()` maps these onto `normalisePreferences()`. `MealPlanScreen.js` has a "Meal preferences" card/toggle UI already built around this.

**5. Recipes** — `recipeImport.js` (web import) extracts only schema.org JSON-LD: `{ name, ingredients: string[], servings }` — ingredients are **raw free-text strings** ("2 cups flour"), not matched to the curated food table or any structured nutrient/allergen source, so allergens are **not derivable** from a web import without new NLP/matching work. `RecipeBuilder`-side local recipes (`recipes`/`recipe_ingredients` tables) store `food_ref` + `quantity_g` per ingredient — since `food_ref` can point at a curated key or a cached `foods` row, allergen tags COULD in principle be derived for curated-key ingredients (via `tagsOf`) but not for arbitrary OFF/USDA-sourced ingredients (no tag data ingested, per #3).

**6. Sync/schema** — `dietPreference` is the only diet-relevant field that syncs to cloud today: mapped in `src/lib/sync/tables/profiles.js` (`FIELD_MAP`: camelCase → snake_case `users_profile.diet_preference`), added by `supabase/migrate_055_diet_preference.sql`, merge-resolved via `conflict.js` `column_updates_at`. All the meal-plan preference fields (`mealPlanExcludeFoods`, `mealPlanExcludeTags`, `mealPlanMealsPerDay`, `mealPlanVariety`, `mealPlanFatConvention`, `mealPlanPeriWorkout`, `mealPlanPinnedMeals`) are explicitly **local-only / not synced** — the code has a comment calling this out and deliberately preserves them by spreading `localProfile` first on pull so they "survive" merges rather than being wiped (they have "no synced column"). A new dietary-preference/allergen field would plausibly extend `users_profile` (new migrate_1xx_*.sql, additive/idempotent per CLAUDE.md rules) and `FIELD_MAP` in `sync/tables/profiles.js`, or — if kept device-local like the current exclusion lists — need no cloud migration at all (multi-device consistency would then be a founder decision).

**7. ED-safety-adjacent framing** — `planPreferences.js` header: "Exclusions can never push a plan below the safety floors: the assembler reports `withinTolerance:false` instead of starving a day to 'make it fit'." `mealPlanAssembler.js` gates on the engine's `floorApplied` flag and existing warning-regex (`/below safe minimum|raising to floor|hard gate|raised to limit loss|rapid|capped/i`) — i.e. dietary exclusions are explicitly designed to never override the ED calorie/FFM floors; they can only make a day flagged "not exactly on target," never underfed. No restriction-framed copy was found in the diet/preferences UI strings themselves (`"Filters the meals Volyume suggests."`, `"Set these first. The plan uses them for today or the week."`) — plain, non-judgemental, consistent with `COACHING_VOICE_SYNTHESIS_LOCKED.md`.

# Facts (second wave): visual design consistency

Raw fact report saved verbatim from a read-only subagent run on 2026-07-09, second-wave ease-of-use hunt (founder request). Evidence for the ease-of-use strengthening pass. Facts only; judgement stays with the main session.

---

**1. THEME**
Both dark and light themes exist (`src/styles/theme.js` lines 30-233): `baseColors` (dark, default) and `lightColors` (COMP-029, "only tokens that differ from dark are listed"). Resolution mechanism: `applyAccessibility(prefs)` (theme.js:400-445) mutates the exported `colors`/`fontSize` objects **in place** at app boot (called from `App.js` before any screen module is required); `resolveThemeChoice` (theme.js:289-303) maps `prefs.theme` of `'light'|'dark'|'system'` (system reads `Appearance.getColorScheme()`) to a concrete palette. There is no React context/provider — it's a mutable-singleton-object pattern, which is why the code comment (theme.js:6-9) states non-Reduce-Motion toggles need an app reload to take effect. `src/screens/SettingsDisplayScreen.js` exposes the actual toggle UI: Appearance segment (dark/light/match phone, line 74-98), and three more switches — Larger Text (line 209-218), Higher Contrast (229-235), Colour-Blind Safe/Okabe-Ito (246-252), Reduce Motion (263-266). Every toggle except Reduce Motion calls `promptRestartForA11y(label)` (defined line 33) after `setAccessibilityPref`, confirming these require a manual app restart to visually apply. `resolvedTheme` (theme.js:285) is a live-binding export used by StatusBar/NavigationContainer chrome.

**2. TYPE SCALE**
Tokens defined: `fontSize` (theme.js:363-373: micro10, xs11, sm13, md16, lg17, xl20, xxl24, xxxl32, display40) and semantic `type.*` roles (theme.js:488-556: display, h1, h2, h3, title, body, bodyStrong, label, overline, caption, bodySm, captionTight, captionStrong) plus `type.num(role)` for tabular figures.
Raw `fontSize:` numeric literal count in the 5 screens: **0** (HomeScreen, AnalyticsScreen, DiaryScreen, PlansScreen, YouScreen — none). Raw `fontWeight: '...'` literal count: **0** in all 5. Token usage instead: `fontSize.xxx` (token, not `...type.x`) appears HomeScreen 26, AnalyticsScreen 12, DiaryScreen 12, PlansScreen 11, YouScreen 1 (62 total); `...type.xxx` spread appears HomeScreen 33, DiaryScreen 23, PlansScreen 29, AnalyticsScreen 14, YouScreen 10 (109 total). So these 5 screens are clean of raw font literals — divergence here is between two *token* idioms (bare `fontSize.md` + hand-set fontWeight/lineHeight vs. the composed `type.role`), not raw magic numbers.

**3. CARD SYSTEM**
Shared primitives: `Card.js` (base surface, tone accent border via `withAlpha(accent, alpha.mid)`, `surface`/`elevated`/`radius`/`padding`/`borderless` props, hairline border always `colors.borderSubtle`), `GradientCard.js` (compatibility shim, forwards to `Card` — "no gradient... the locked rule is a flat background, no gradients/orbs/glows"), `PressableCard.js` (press physics only, no visual treatment of its own).
`<Card` JSX usage counts across the 5 screens: YouScreen 4, PlansScreen 9, DiaryScreen 1, AnalyticsScreen 7, HomeScreen 4 (25 total).
Contrast: direct `backgroundColor: colors.surface*` in local StyleSheets: YouScreen 2, PlansScreen 14, AnalyticsScreen 4, HomeScreen 13, DiaryScreen 18 (51 total); direct `borderWidth: 1` in local styles: YouScreen 1, PlansScreen 10, DiaryScreen 13, AnalyticsScreen 4, HomeScreen 18 (46 total). DiaryScreen in particular has only 1 `<Card>` component usage against 18 local `backgroundColor: colors.surface*` blocks and 13 local `borderWidth: 1` blocks — i.e., it mostly builds its own card-like containers rather than the shared component. `shadow.*` token usage across all 5 screens: 1 occurrence total (DiaryScreen). So the visible card treatments are a mix of (a) the shared `Card` component's surface+borderSubtle+radius.lg recipe and (b) numerous per-screen hand-rolled `View` blocks using `colors.border` (the stronger token) rather than `colors.borderSubtle`, plus varying `borderRadius: radius.md` vs `radius.lg` vs `radius.full` combinations, and one raw `borderRadius: 24` literal (HomeScreen.js:3033).

**4. SPACING RHYTHM**
Token: `spacing` (theme.js:334-345: hair1, xxs2, xs4, xs2:6, sm8, md12, lg16, xl24, xxl32, xxxl48). `spacing.*` token usage counts: YouScreen 13, PlansScreen 46, DiaryScreen 64, AnalyticsScreen 43, HomeScreen 106 (272 total). Raw numeric literals in margin/padding/gap/position/size properties: YouScreen 8, PlansScreen 17, DiaryScreen 21, AnalyticsScreen 11, HomeScreen 37 (94 total, broad regex including width/height/top/etc., not spacing-only). Narrower margin/padding/gap-only raw-number scan found concrete off-scale examples: HomeScreen.js `paddingVertical: 14` (line 2567, no token matches 14), `gap: 3` (2391), `gap: 6`/`gap:10`/`gap:14` (2461, 2914/2923, 3020), `marginTop: 2` used raw multiple times (2560, 2956) even though `spacing.xxs` = 2 already exists as a named token; PlansScreen `paddingVertical: 3` (1166, 1238); AnalyticsScreen `paddingVertical: 3` (diffChip, 1181). So off-scale raw values (2, 3, 6, 10, 14) recur, several duplicating an existing token value by coincidence rather than referencing it.

**5. ICONOGRAPHY**
All 5 screens import only `Ionicons` from `@expo/vector-icons/Ionicons` — no other icon family. Convention is mixed outline/filled by semantic intent (e.g., `chevron-forward`, `close`, `barbell-outline`, `checkmark-circle`, `play` vs `play-outline`) — not a single blanket outline-or-filled rule.
`iconSize` tokens (theme.js:687-692: sm16, md20, lg24, xl32) are used via `size={iconSize.sm}` etc. only 22 times total across the 5 screens (HomeScreen 10, DiaryScreen 6, PlansScreen 2, AnalyticsScreen 2, YouScreen 2). Raw numeric `size={N}` literals number roughly 80+ across the same 5 files, with values including 12, 13, 14, 15, 16, 18, 19, 20, 21, 22, 24, 26, 28, 56 — several of which (13,14,15,19,21,22,26,28,56) don't correspond to any `iconSize` token at all.

**6. CONTRAST**
Dark theme (theme.js:104-107): `textPrimary: '#FFFFFF'` (19.44:1 on bg, AAA), `textSecondary: '#9E9E9E'` (7.25:1 on bg, "AAA body, AA on raised surfaces"), `textMuted: '#9C9C9C'` (7.08:1 on bg), `textDisabled: '#727272'` (4.04:1). Light theme (theme.js:213-216): `textPrimary: '#1A1A18'`, `textSecondary: '#555553'` (~7.5:1), `textMuted: '#5C5C5A'` (>=5.5:1 on every surface), `textDisabled: '#8E8E8A'`. Background dark `#0D0D0D` (deliberately not pure black, "halation" comment lines 31-33); light background `#FAFAF7` (deliberately not pure white, "glare" comment line 186).
Divergence noted directly in theme.js comments themselves: `textSecondary` and `textMuted` are two separate tokens with near-identical values/purposes (dark: 9E9E9E vs 9C9C9C, 7.25:1 vs 7.08:1 — a 1-value RGB difference) and overlapping documented roles ("AAA body" vs "AAA at body-text bar"), i.e., the token split's practical distinction is thin. Also flagged in-file: `chipInk` (theme.js:132-139) is a rename-split of `camera` because `ScreenHeader.js` was borrowing the narrowly-scoped `colors.camera` token (reserved for the live-viewfinder surround) for an unrelated decorative chip — a documented past divergence between a token's stated purpose and its usage.

**7. STRONGEST CONSISTENCY FACTS**
1. Zero raw `fontSize:`/`fontWeight:` literals in any of the 5 screens — full adoption of tokens for basic type properties.
2. All 5 screens use exactly one icon family (Ionicons), no mixing of icon sets.
3. All 5 screens import and use the shared `Card` component (not zero adoption anywhere), and none imports `GradientCard` directly (correctly treating it as legacy/shim per its own file comment).
4. `spacing.*` token usage (272 occurrences) substantially outweighs raw-number usage in layout properties across the 5 screens.
5. `borderRadius: radius.*` token usage dominates in DiaryScreen (e.g., DiaryScreen.js:1893-2170, ~20+ `radius.md`/`radius.lg`/`radius.full` uses) with only a single raw `borderRadius: 24` literal found across all 5 screens (HomeScreen.js:3033).

**5 STRONGEST DIVERGENCE FACTS**
1. DiaryScreen.js: only 1 `<Card>` component usage vs. 18 local `backgroundColor: colors.surface*` blocks and 13 local `borderWidth: 1` blocks — the screen's "cards" are almost entirely hand-rolled outside the shared component.
2. DiaryScreen.js hand-rolled card-like boxes use `borderColor: colors.border` (lines 1968, 2001, 2012, 2022, 2049, 2058, 2069, 2083, 2088, 2097, 2105, 2118, 2142) — the stronger/WCAG-edge border token — where `Card.js` (line 128) deliberately uses the quieter `colors.borderSubtle` for card hairlines; same pattern in HomeScreen.js (2467, 2600, 2720, 2803, 2838). This is a directly contradictory choice vs. the documented rule in `Card.js`'s own comment ("Cards use the quiet borderSubtle token").
3. Icon sizing: only 22 uses of `iconSize.*` tokens vs. ~80 raw numeric `size={}` values spanning at least 13 distinct raw numbers (12,13,14,15,16,18,19,20,21,22,24,26,28,56), several with no corresponding token (13,14,15,19,21,22,26,28,56) — e.g. HomeScreen.js lines 1407/1457/1511/1543/2009 all use raw `size={16}` (equal to `iconSize.sm`) instead of the token, alongside genuinely off-scale values like `size={15}` (1483) and `size={14}` (1599, 1874, 2400).
4. Off-scale raw spacing values recur despite full token coverage: HomeScreen.js:2567 `paddingVertical: 14` (no `spacing` step is 14); HomeScreen.js gap values of 3, 6, 10, 14 (lines 2391, 2461, 2914, 2923, 3020) sit beside 272 correct token uses in the same file.
5. `shadow.*` tokens (sm/md/lg/glow) appear only once across all 5 screens combined (DiaryScreen), despite `theme.js`'s documented "VOLYUME MATERIALS POLICY" (lines 11-29) stating light-theme elevation should be primarily carried by shadow — the 5 screens' local styles almost never reference `shadow.*`, relying on the surface ladder and ad hoc borders instead, which is consistent with dark-theme convention but leaves the light-theme shadow cue largely unexercised in these screens' own styles (elevation there depends on whatever `Card`/other components supply, not screen-local code).

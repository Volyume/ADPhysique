1. How to read this

This is a map, not source code. You don't need to know how to program to use it. The point is to give you, the founder, a way to check whether the app actually does what it says it does, without opening any code file.

Each section answers one question:

  • What is here? — what feature, what screen, what it's for.
  • Is it working? — a coloured pill (green / amber / red) tells you at a glance.
  • What connects to what? — diagrams show how screens link, where data comes from, where it goes.
  • What's broken or missing? — flagged explicitly with the file or table it relates to.

You can sideload an APK on your phone and walk through any flow on this page step by step to confirm what it says.

2. Status legend

Built — implemented end-to-end, tested or manually verified
Partial — exists but missing pieces (e.g. data layer wired, UI absent)
Missing — no code, no UI, not built
Deferred — explicitly out of scope per spec or founder decision

Where a feature is partial, the "what's missing" column tells you exactly which piece.

3. The app in one paragraph

Volyume is an Android-only training + nutrition logbook with an automatic weekly coach. The user trains, logs food, weighs in, and ticks a weekly check-in. Every week the coach computes whether the body weight trend matches the goal and adjusts calorie targets up or down (within safety floors) and surfaces volume / RPE suggestions for training. The Free tier covers logging; Pro adds the coach output, body composition, and the food layer's deeper insights. All data is stored on-device in SQLite and synced to Supabase in the background; sign-out wipes the device, account deletion wipes everything end-to-end.

What's missing on the Diary tab

Recipe builder Missing

The database tables (recipes, recipe_ingredients) exist with full cloud sync wired. There is no screen registered to create, edit, or pick a recipe. The Search tab's "My Recipes" section per UI_FLOWS_LOCKED.md is absent.

Saved meals / meal templates Missing

The saved_meals table exists. Helpers (getAllSavedMealsSince, applySavedMealFromCloud) exist in src/lib/food/db.js. Cloud round-trip works. No UI to save a meal as a template or apply one. The Search tab's "My Meals" section per the spec is absent.

Food dislikes / exclusions Missing

"Like" is implemented as food_favourites (heart on every row). "Dislike" / "don't suggest this" has no table, no UI, no helper. The coach can't avoid suggesting foods the user has explicitly said they won't eat.

  • Built Check-in form persists every field.
  • Built runWeeklyCoach() in src/lib/weeklyCoach.js tested at the algorithm layer (50+ assertions, 10+ simulator scenarios). Caps adjustments at ±300 kcal/week (±120 at low confidence).

16. Where data lives in the cloud

The cloud is Supabase (Postgres + RLS + Edge Functions). Every user-scoped table has Row Level Security ON; users can only read / write their own rows.

The sync registry — the master list of which tables sync — has 16 tables:

"Last-write-wins" means: when both device and cloud have a row with the same id, whichever side has the newer updated_at timestamp wins. "Per-column merge" (only for profiles) means: each field can be updated independently — Device A changes first_name, Device B changes units, both land safely. The merge is gated by a column_updates_at JSON column on the cloud side.

The audit query at supabase/audit_cloud_schema_drift.sql can be run any time in the Supabase SQL Editor to verify every column the client expects is present on the cloud. (Run it after every sync handler change.)

17. How data syncs between device and cloud

flowchart LR Write[User write on device] Write --> Local[SQLite saved immediately] Local --> Queue[pending_sync_ops queued] Local --> UI[UI updates instantly] Queue --> Trigger{Sync trigger} Trigger -- App foregrounds --> Run[syncAll] Trigger -- Network reconnects --> Run Trigger -- Debounced write --> Run Trigger -- 15-min interval --> Run Run --> Push[Per-table push for migrated tables - then legacy bulk] Push --> Cloud[Supabase] Cloud --> Pull[Per-table pull for migrated tables - then legacy bulk] Pull --> Merge[LWW + soft-delete + tombstone propagation] Merge --> Local2[SQLite updated from cloud] Local2 --> UI2[UI re-renders if focused]

How it actually works

  • Every write hits SQLite first. The UI updates instantly. The user never waits on the network.
  • The write is queued in pending_sync_ops for later push.
  • One of four triggers fires syncAll: app foregrounds, network reconnects, debounced after a write, or every 15 minutes.
  • The 16 registered tables push and pull individually; legacy bulk push/pull handles anything not yet migrated to the per-table transport.
  • The sync status badge in the navigation header shows synced / pending / offline / error with a tap-for-details sheet.

What was checked

  • Built All 16 registered tables on per-table transport (src/lib/sync/tables/ — one file per non-food table, food-domain coordinator for the 7 food tables).
  • Built Regression matrix at src/lib/sync/__tests__/sync.regressionMatrix.test.js — 50 actionable assertions across every table for insert / update / soft-delete / pull / conflict / push-error scenarios. Tests against mocked Supabase, fast.
  • Built Schema drift audit at supabase/audit_cloud_schema_drift.sql — pasted into Supabase SQL Editor returns any client-vs-cloud column mismatches.
  • Out of scope (deleted 2026-05-27) Live-cloud two-device propagation tests (T7 / T8 from the testing spec). The scenario doesn't apply to an Android-only single-device product. Sign-out + sign-in on a new handset is manually tested per release.

23. Glossary for non-coders

Screen
One page the user sees. Home, Diary, Settings, etc. The app has 56 of them.
Tab
The icons across the bottom of the app. Volyume has 5: Train / Plans / Diary / Progress / You.
Modal
A screen that pops up on top of whatever you were doing, like the barcode scanner or the paywall.
Stack
The sequence of screens you can go back through with the back button.
SQLite
The database that lives on the phone itself. Survives an offline trip. Survives a flight.
Supabase
The cloud database. Where data lives when the phone isn't to hand.
RLS (Row Level Security)
Postgres feature that means user A literally cannot query user B's rows, even if they tried.
RPC (Remote Procedure Call)
A function that lives in the cloud database and gets called by the app. Used for things like upgrading a tier or computing daily rollups.
Sync
Copying changes between the phone and the cloud. Bidirectional: phone pushes its writes; phone pulls cloud changes.
LWW (Last-Write-Wins)
The conflict rule: if the phone and cloud both have a row with the same id, whichever side has the newer timestamp wins.
Tombstone
A "deleted" row that hasn't actually been removed yet. Kept around so the deletion can be synced before being purged.
FFM (Fat-Free Mass)
Your body weight minus your body fat. Used for the safety floor: nobody should be eating below 30 kcal per kg of FFM per day.
e1RM (estimated one-rep max)
What you could probably lift for one rep, calculated from a heavier set. Standard formula, reliable for 1-15 reps.
Mesocycle
A multi-week training block, typically 4-6 weeks of progressive load + 1 week deload.
Deload
A planned easy week to recover. Volume drops to ~60% of the previous week.
MEV / MAV / MRV
Minimum Effective Volume, Maximum Adaptive Volume, Maximum Recoverable Volume. The set-count ranges per muscle group per week. Defaults from Renaissance Periodization, currently not per-user calibrated.
Cascade
The trial-to-Free downgrade flow. Day 19 warning, day 21 auto-downgrade unless the user pays.
RTDN (Real-Time Developer Notifications)
The Google Cloud Pub/Sub stream that tells the backend a user's subscription state changed (purchased, renewed, cancelled, refunded).
Article 9
The UK GDPR section that covers health and nutrition data. Requires explicit, separate consent — not buried in the ToS.
SCOFF
A short clinical screener for disordered eating risk. Asked once during onboarding.
ED-pattern detector
Multi-signal harm check that fires if the user shows several markers of eating-disorder behaviour. Locks the coach from suggesting further calorie reductions.
Goal lock
Self-attested experience flag that has to be ticked for advanced goals like physique competition. Raises the ED-pattern detector's threshold (more signals required to fire).
